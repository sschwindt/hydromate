# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A TELEMAC hydro-morphodynamic model of a reach of the **Inn river in Bavaria, Germany**. The goal is a 2D depth-averaged hydraulic + sediment-transport simulation (TELEMAC-2D coupled with GAIA), set up automatically and calibrated with quantified uncertainty via [HydroBayesCal](https://github.com/Ecohydraulics/hydrobayescal).

**Overarching aim:** largely automate *both* sides of the workflow around HydroBayesCal - **pre-processing** (geodata → ready TELEMAC case) and **post-processing** (field **ground-truth** → calibration targets + result extraction). Pre-processing (stages 1–5) is built for the 2D hydraulic path; the **post-processing / ground-truth ingestion is the active frontier** (turning FlowTracker velocity/depth, grain-size distributions, and DEM-of-Difference topographic change into the calibration-points CSV and GAIA inputs HydroBayesCal consumes). See "Ground-truth & calibration data" below.

The tracked repository is the **`hydromate` package** (`src/hydromate/`) plus a data-free **`cases/case-template/`** scaffold (config + the workflow scripts `preprocessing.py` / `initial_run.py` / `mesh_convergence_study.py` / `run_Bayes_cal.py` and the multi-discharge variant `run_Bayes_cal_multiflow.py`, the optional 3D extension `add3d.py` / `vertical_convergence_3d.py`, and the optional unsteady extension `unsteady_run.py` + `USAGE.info` + `user-sources/README.md`, the starting point for a new case) and the worked example case under `cases/example-Inn/` (its `case-config.yml`, `preprocessing.py`, `initial_run.py`, `mesh_convergence_study.py`, `add3d.py`, `vertical_convergence_3d.py`, `run_Bayes_cal.py`). Each case lives in `cases/<name>/` and keeps only those tracked files; the real Inn **input data** (DEMs, orthos, zone GeoPackages, gauge data, ground truth) is large (~5 GB) and lives in `cases/example-Inn/user-sources/` for co-development only, while produced artifacts land in `cases/example-Inn/hydromate-case/`, split by workflow phase: `preprocessing/` (DEM clips, meshes, ground-truth table), `simulation/` (the TELEMAC case build + results, incl. the 3D `<case>3d.cas`), `postprocessing/` (general post-processing, plus `mesh-convergence/` grid-independence and `vertical-convergence/` 3D layer studies), `calibration-validation/` (HydroBayesCal artifacts). Each phase's script writes its outputs and its `hydromate.log` into its own subfolder. Both `user-sources/` and `hydromate-case/` are **gitignored** (`.gitignore` ignores `cases/*/user-sources/` and `cases/*/hydromate-case/`, plus a safety net of binary/geo extensions `*.tif/*.gpkg/*.shp/*.xlsx/*.slf/*.log/...`); a CI workflow (`.github/workflows/file-size-limit.yml`) additionally fails any push/PR with a tracked file over 20 MB. Don't assume the data files are present in a fresh checkout. See `README.md` for the workflow and `cases/example-Inn/case-config.yml` for the case config (a commented template; all paths resolve relative to the config file's directory).

## The `hydromate` workflow

`hydromate cases/example-Inn/case-config.yml` runs a 5-stage pipeline (`src/hydromate/pipeline.py`):

1. `dem.py` - reproject + clip the initial (and optional target) DEM to the ROI boundary. When `dem_of_difference.enabled` (or `morphodynamics.enabled`), also computes the **DEM-of-Difference** (`dem.dem_of_difference`, `dem_target - dem_initial` on the ROI-clipped initial grid) thresholded by a **minimum level of detection** (`dem.resolve_lod`): an explicit `dem_of_difference.min_lod`, else the propagated survey uncertainty `t·√(uncertainty_initial² + uncertainty_target²)` (`dem.propagated_lod`, `t` from `confidence_level`); sub-LoD cells are masked to nodata (`mask_below_lod`) or zeroed, and the net/erosion/deposition volumes are logged. A precomputed `geodata.dem_of_difference` short-circuits the computation.
2. `mesh.py` + `selafin.py` - gmsh triangular mesh; DEM interpolated onto nodes; geometry written as SELAFIN with a `FRIC_ID` per-node variable (so no separate ZONES FILE is needed). The geometry is written in **double precision** (SERAFIND); single precision collapses sub-metre cells on UTM coordinates (see `selafin.py` design point). `build_mesh` prunes gmsh's geometry/1D-only nodes to triangle-referenced nodes (no orphans/duplicates), enforces consistent CCW winding, then runs `mesh_quality.assess_quality` (logged via `log_report`, stored on `Mesh.quality`). The mesh boundary is walked to build IPOBO, which **must** stay consistent with the `.cli` row order. **Two meshing strategies** (auto-selected): *anisotropic* (when `geodata.mesh_zones` + `geodata.channel_centerline` are set) types each mesh-zone polygon `channel`/`floodplain`/`refinement` (by `Zone Name` substring) and sizes it by its own `Max Edge Length (m)` field - channel cells elongated along the centerline, floodplain/refinement near-equilateral - via a metric-tensor background view + gmsh **BAMG** (`Mesh.Algorithm=7`); *isotropic fallback* uses `default_size`/`breakline_size`/`region_sizes` distance fields. See "Meshing" below.
3. `boundary.py` - classify contour nodes against the liquid-boundary lines and write the `.cli`. The lines come from `boundaries.liquid_boundaries` (a line layer whose `Type (inflow/outflow)` field - note the Inn file's typo `Type (inflow/outlfow)`, still detected - tags each line `inflow`/`outflow`; several of each allowed) and must coincide with the mesh-zone outer bounds. Codes: solid wall `2 2 2` (every non-liquid outer node), inflow `4 5 5` (prescribed Q, depth free - `LIHBOR` must be 4 not 5, else the inflow depth is forced to the inflow's PRESCRIBED ELEVATIONS slot of 0 and TELEMAC's DEBIMP aborts on a dry inflow), outflow `5 4 4` prescribed-elevation (the default `boundaries.outflow_condition: elevation`, a fixed WSE from `boundaries.prescribed_elevation`; or `stage_discharge` for a WSE from the rating curve at the simulated Q) or `4 4 4` free/Neumann (`outflow_condition: free`, needs no WSE). Matching tolerance is tied to the local edge length (anisotropic: ~2×`floodplain_size`). If total inflow- vs outflow-node counts differ by >10%, a stability-risk warning is logged.
4. `steering.py` - friction `.tbl` (one row per friction zone: `<id> <LAW> <coef> NULL`, ends with `END`; comments only on `*` lines - rows come from `friction.zones`/MATID or, failing that, the roughness table as `<Zone ID> NIKU <ks> NULL`) and the Telemac2d `.cas`; GAIA `.cas` when enabled. The **default solver is the classic finite-element kernel** (`hydrodynamics.finite_volumes: false`); set it true for the HLLC finite-volume kernel (robust on transcritical wetting/drying but constant-viscosity only). The **turbulence model is auto-selected** (`hydrodynamics.turbulence_model: auto`) by `steering.select_turbulence_model(cfg, mesh)` from the channel cell size relative to the turbulence length scale (the flow depth) and the velocity guess `initial_velocity_guess` (U≈1 m/s): **Smagorinski LES (4)** when the mesh resolves ≥80% of the TKE (`dx/L ≤ 0.2^1.5`, ~11+ cells/L - the LES validity gate), **k-epsilon (3)** at moderate resolution (≥~4 cells/L), **Spalart-Allmaras (6)** on coarse meshes; an explicit int/name overrides, and finite volumes force model 1. The **initial run is always steady** (`steady2d.cas`). The FE numerics are written **compute-stable by default** to keep the wetting/drying steady march from exploding: `time_step` is only a conservative CFL **start** step (0.25 s) while `desired_courant` (0.30) drives the adaptive marching step, `IMPLICITATION FOR DEPTH/VELOCITY` 0.80 (config `implicitation`), `FREE SURFACE GRADIENT COMPATIBILITY` 0.9, `DISCRETIZATIONS IN SPACE : 11;11` (linear FE, required by the distributive advection scheme 14), `NUMBER OF SUB-ITERATIONS FOR NON-LINEARITIES`/`MAXIMUM NUMBER OF ITERATIONS FOR ADVECTION SCHEMES`, `H CLIPPING : NO`, and a raised k-epsilon solve budget (`MAXIMUM NUMBER OF ITERATIONS FOR K AND EPSILON`, config `max_keps_iterations`). The graphic printout is `'U,V,S,B,H,M,Q,F'` plus `K,E` (TKE + dissipation) **for the k-epsilon model (3)**. **Time bound:** with the default `variable_timestep` the run is capped by `DURATION` (the explicit `hydrodynamics.duration` in seconds, else the `n_time_steps × time_step` fallback - so a small CFL start step no longer shrinks the simulated time), **not** `NUMBER OF TIME STEPS` - the latter does **not** terminate a variable-dt run (the CFL-driven dt is unknown a priori), so it would otherwise be unbounded. Convergence is judged by the **boundary-flux balance** (`initial_run.py` → `hydromate.flux_convergence` / pythomac), not by the solver. **The steady-state auto-stop is OFF by default** (`hydrodynamics.stop_if_steady: false`) and is hard-suppressed whenever `variable_timestep` is on: TELEMAC's `steady.f` stops when the change between **two consecutive time steps** falls below `STOP CRITERIA`, but that is an **absolute per-step** change (order **H ; (U,V) ; tracers** in `steady.f`; the dico's English help listing (U,V) first is wrong), and with the tiny CFL dt it false-fires during a slow transient (e.g. a low-Q reach still filling from a dry start) **long before the fluxes balance** - the run halts far from steady state (the symptom: it stops with inflow ≠ outflow). It is emitted only for a steady **fixed-step** run (`variable_timestep: false`, where a per-step change is meaningful), never for the unsteady run, and **TELEMAC-3D has no equivalent keyword**. When `boundaries.inflow` carries a *varying* hydrograph, `pipeline.run` additionally writes `unsteady2d.cas` (DURATION from the series) plus a TELEMAC liquid-boundaries file (`inflow-hydrograph.liq`, `Q(t)` per inflow / `SL(t)` per prescribed-elevation outflow via `steering.write_liquid_boundaries`). The steady inflow Q comes from `boundaries.prescribed_flowrate` (the optional `boundaries.inflow` series, read by `hydraulics.py`, is only for a varying hydrograph / unsteady case). The outflow water-surface elevation is needed for the prescribed-elevation conditions: the default `boundaries.outflow_condition: elevation` uses `boundaries.prescribed_elevation`, while `stage_discharge` interpolates `boundaries.stage_discharge` (a Q-h CSV; one pair suffices for steady) at the simulated Q; `free` prescribes nothing. When no measured rating curve exists, `hydromate.rating.generate_stage_discharge` (CLI: `hydromate rating`) synthesises one from a Manning `n`/Strickler `Kst` and a trapezoidal channel geometry by inverting Manning's normal-flow equation; `rating.synthesize_outflow_rating(cfg, Q)` derives the geometry from the case data (width = outflow liquid-boundary line length, bed = DEM thalweg along it, slope = reach slope from the DEM along the centerline, roughness = `friction.boundary_*`) and `cases/example-Inn/preprocessing.py` (and the convergence-study script) call it to auto-generate `boundaries.stage_discharge` when missing. The lateral-boundary friction keywords (`LAW OF FRICTION ON LATERAL BOUNDARIES` / `ROUGHNESS COEFFICIENT OF BOUNDARIES`) come from `friction.boundary_law` / `boundary_coefficient` (Inn: Strickler 38).
5. `ground_truth.py` + `calibration.py` - compile the configured `ground_truth.sources` into the **tidy multi-tab table** (`ground_truth.compile_ground_truth`, written to `preprocessing_dir/ground-truth.xlsx` unless `ground_truth.measurements` overrides), then turn it into `measurements-calibration.csv` and the HydroBayesCal `config_Telemac.py` (both in `calibration_dir` = `calibration-validation/`).

`pipeline.run()` returns an `Artifacts` dataclass listing every produced path; `cli.py` logs these. The package's public API (`hydromate/__init__.py`) exports `Config`, `load_config`, `clip_to_roi`, `clip_dem_to_roi`, the DoD helpers `dem_of_difference` / `propagated_lod` / `resolve_lod`, `compile_ground_truth`, `read_tidy`, the mesh helpers `build_mesh` / `channel_node_mask` / `interpolate_elevations` / `interpolate_roughness` / `write_mesh` / `assess_quality`, the rating-curve helpers `generate_stage_discharge` / `normal_depth` / `synthesize_outflow_rating`, the turbulence helpers `select_turbulence_model` / `eddy_viscosity_estimate`, the TELEMAC-3D helpers `build_3d_cas` / `infer_vertical_layers` / `select_3d_turbulence` / `run_vertical_convergence` / `layer_levels`, the mesh-convergence helpers `run_mesh_convergence` / `percent_levels`, the shared per-case workflow helpers `prepare_steady_inputs` / `resolve_discharge` / `synthesize_constant_inflow` / `synthesize_rating_if_missing` / `format_flux_convergence` / `run_solver_streaming` / `expected_duration` (`hydromate/workflow.py` - the logic the per-case `preprocessing.py` / `initial_run.py` / `mesh_convergence_study.py` scripts share, so they stay thin), the live solver-progress renderer `SolverProgress` (`hydromate/progress.py`), and the logging helpers `setup_logging` / `log_step` / `logging_to`. `mesh.build_mesh(cfg)` (no DEM) yields a bare mesh; `interpolate_elevations(mesh, dem, decimals=4)` fills the bottom from a raster (rounded); `write_mesh(mesh, path)` writes a geometry SELAFIN. These low-level helpers let you build a mesh programmatically; the worked example's `preprocessing.py` instead drives the full `pipeline.run` build (writing `geometry.slf` etc. into `simulation/`; see the workflow below).

### Meshing (stage 2)

The mesher is **gmsh**, chosen over the SALOME/Q4TS route (which the working Inn model historically used) because gmsh is pip-installable, fully headless/scriptable, and supports the anisotropic meshing needed here - whereas Q4TS runs inside SALOME's GUI/SMESH stack and is heavyweight/version-sensitive to automate. SALOME lives at `/home/schwindt/opt/salome/` if ever needed.

- **Anisotropic, flow-aligned channel** (the requirement): channel triangles are *elongated along the channel centerline*, floodplain triangles near-equilateral, with a smooth transition. Implemented exactly like gmsh tutorial **t17**: build a coarse background triangulation (a Delaunay grid over the ROI bbox, node-budget-capped ~40k so any domain fits in memory), assign each background node a **3×3 metric tensor** (eigenvalue = 1/h²; anisotropic `1/(channel_size·anisotropy)²` along the local centerline tangent and `1/channel_size²` across, inside `channel` zones; isotropic `1/floodplain_size²` elsewhere), push it as a `TT` list **PostView** + `setAsBackgroundMesh`, then mesh with **`Mesh.Algorithm=7` (BAMG)**, `Mesh.SmoothRatio=growth_ratio`, `Mesh.AnisoMax`. The coarse background also produces the smooth channel→floodplain blend (gmsh interpolates the metric within each background triangle).
- Zone selection is by **substring** of the `Zone Name` attribute (case-insensitive): `*channel*` vs `*floodplain*` in `geodata.mesh_zones`. The centerline (`geodata.channel_centerline`) is sampled and `np.gradient` gives per-vertex tangents (nearest via `cKDTree`).
- BAMG **approximates** the metric: realised cross-channel size and anisotropy come out a bit gentler than the configured targets, and `growth_ratio` (default 1.2) intentionally relaxes them near banks. Knobs: `mesh.channel_size` 0.5, `floodplain_size` 1.5, `growth_ratio` 1.2, `channel_anisotropy` 4.0, `max_aspect_ratio` 4.0. Defaults are **high-res**: the Inn KB15 ROI (~0.32 km², ~130 m-wide channel) yields ~720k elements / ~360k nodes (~90 s, ~0.7 GB; the aspect cap below tightens `AnisoMax` which refines the mesh) - raise the sizes while iterating.
- **Aspect-ratio cap** (`mesh.max_aspect_ratio`, default 4.0 = longest:shortest edge): BAMG overshoots the metric anisotropy in the tail (~1.6x) and leaves a few channel slivers, so `Mesh.AnisoMax` is set to `max_aspect_ratio/1.6` and a post-mesh **edge-flip** pass (`_flip_sharp_edges`) flips the shared (long) edge of over-sharp cell pairs - a topological repair that touches only the offending cells (boundary untouched, IPOBO/winding preserved, no inversions), bringing the realised channel max from ~6.5:1 down to ≤~4:1 while keeping the bulk elongation (channel aspect median ~2.0 vs floodplain ~1.4).
- **BAMG failure retry** (`build_mesh`, `_BAMG_RETRY_LADDER`): at fine, high-contrast anisotropic metrics (e.g. a small `refinement` zone next to a coarser floodplain, hit as the mesh-convergence study refines) BAMG's Delaunay insertion can abort with `Fatal error in the meshgenerator 1001 / BAMG failed`. Empirically a **coarser** background metric grid rescues it (larger background triangles smooth the interpolated size gradient BAMG must honour; a *denser* grid makes it worse), as does a looser `Mesh.AnisoMax`. `build_mesh` therefore retries `gmsh.model.mesh.generate(2)` on a BAMG failure with a ladder of `(background node budget, AnisoMax relaxation)` each gentler than the last (`(40000,1.0) -> (20000,1.0) -> (10000,1.5) -> (6000,2.5)`) before re-raising; the normal path meshes on the first (default) attempt with no retry. Isotropic meshing has a single attempt.
- The **isotropic fallback** (no mesh_zones/centerline) is the original distance-field path (`default_size`/`breakline_size`/`region_sizes`); the integration test exercises it.
- **Quality assessment** (`mesh_quality.py`, vectorised, scales to the ~525k-element mesh): logs per-region (channel vs floodplain, via a centroid-in-`_channel_union` mask) internal angles, aspect ratio, skewness; the **shortest edge** (flagged as CRITICAL for the CFL-limited adaptive time step); and the fraction of adjacent-cell area jumps over `mesh.max_area_jump` (20%). The channel is `relaxed=True` so its *intended* anisotropy (aspect ≫ 1) is reported but never warned on - shape warnings (angle < `min_angle_deg`/> `max_angle_deg`, high aspect) apply to the floodplain only. Fatal defects (zero-area, inverted/mixed-orientation, duplicate nodes, non-manifold edges) **raise**; orphan nodes, extra boundary loops (hanging gaps) and IPOBO mismatch (wrong boundary tags) warn. Thresholds are `mesh.min_angle_deg`/`max_angle_deg`/`max_area_jump`.
- Meshing (mesh-zones) and friction (roughness-zones) are **separate concerns**: `geodata.mesh_zones` only sizes the mesh. Friction zonation comes from `geodata.roughness_zones` (an integer `Zone ID` per polygon): `mesh.interpolate_roughness(cfg, mesh)` tags every node/element with the `Zone ID` it falls in (nearest polygon otherwise), writes it as the per-node `FRIC_ID` (overriding the MATID-derived ids), and stores the `roughness_table` value for that id as the `BOTTOM FRICTION` variable. `mesh.run` (hence `pipeline.run`) calls it whenever `roughness_zones` + `roughness_table` are set, so the built `geometry.slf` carries the zone `FRIC_ID` + `BOTTOM FRICTION`, and `steering.write_friction_tbl` derives the matching `.tbl` rows (`<Zone ID> NIKU <ks> NULL`, law `friction.roughness_law`, default 5) from the same table. HydroBayesCal perturbs each `ks` via `zone1`/`zone2`.

Key design points:
- The build runs in its **own** `hydromate-env` conda env (gmsh/geopandas/rasterio); it does not import TELEMAC's Python. `env.py` *sources* `telemac.pysource` (the `pysource.*.sh`) in a subshell for any solver/SELAFIN call. The config's `telemac.pysource` must point at the real script (e.g. `/home/schwindt/opt/telemac/configs/pysource.mint22.sh`).
- Friction zonation has two routes: (a) the **roughness-zones** route - `geodata.roughness_zones` (`Zone ID`) + `geodata.roughness_table` (id→ks) drive the per-node `FRIC_ID` and `BOTTOM FRICTION` via `interpolate_roughness` (preferred for the Inn case; see the Meshing section); (b) the older **MATID** scheme (1 riverbed_fine … 5 floodplain; see table below) carried by `geodata.region_points` + `geodata.region_table` and/or `friction.zones` in the config → friction `.tbl` rows and `zone<MATID>` calibration parameters. Either way HydroBayesCal perturbs the coefficient column of the `.tbl`. `steering.write_friction_tbl` builds the `.tbl` in priority order: explicit `friction.zones` (MATID) > the roughness table (one `<Zone ID> NIKU <ks> NULL` row each) > a single default zone - so the `.tbl` rows always match the geometry's per-node `FRIC_ID`.
- `src/hydromate/selafin.py` is a self-contained big-endian SELAFIN writer (plus a `read_slf` reader for results); its output is validated against TELEMAC's own `data_manip.formats.selafin.Selafin` reader in the tests.
- **Logging** (`src/hydromate/logsetup.py`): each script/phase writes a compound, timestamped `hydromate.log` into its **own output folder** (`setup_logging(path)` routes the `hydromate` logger and captured Python warnings to it; file at DEBUG, console at the chosen level, append mode). the build (`pipeline.run`, called by `preprocessing.py`; and `initial_run.py`'s test run) -> `model_dir` (`simulation/`), the mesh-convergence study -> `mesh-convergence/` (scoped via the `logging_to(path)` context manager so it doesn't capture the per-level builds elsewhere). `log_step(name)` logs `START`/`DONE … in N.NNs` (or `FAILED … after N.NNs`) - wrapped around every pipeline stage and the heavy mesh/convergence sub-steps for per-step timing. `pipeline.run(..., log_to_file=False)` skips its own logfile (the convergence study's per-level builds use this so they log only to `mesh-convergence/hydromate.log`). Tests reset handlers via an autouse fixture (`tests/conftest.py`).
- **Initial condition - DRY START (default) vs pre-wetting**: the initial run is a **dry start** by default. A *fully* dry bed (`ZERO DEPTH`) can't be used because TELEMAC's `DEBIMP` aborts at a prescribed-Q inflow when the inflow cross-section is dry (it scales the velocity profile by Q/Q1 with Q1 ∝ ∫H along the inflow; H=0 ⇒ Q1=0 ⇒ abort, even with the correct `4 5 5` code - see the inflow-cli memory). So `steering.write_dry_start_conditions` seeds a thin water **plug only on the nodes within `initialization.dry_start_extent` of the inflow line(s)** (default ~5 cells) to `dry_start_depth` (default 0.5 m, kept ≥ normal depth so the inflow stays subcritical) and leaves the rest of the domain **dry**; the `.cas` continues from this SELAFIN (`PREVIOUS COMPUTATION FILE` + `INITIAL TIME SET TO ZERO : YES`) and the flow wets the reach from the inflow. The inflow geometry comes from `boundary._load_liquid_lines`; with no inflow line it falls back to the analytical dry `INITIAL CONDITIONS`. **Pre-wetting** (`initialization.prewet_depth`, m) is the *alternative*: when set, stage 4 instead hotstarts the **whole `*channel*` mesh-zone** to that depth (`write_initial_conditions` + `mesh.channel_node_mask`, thalweg-following surface) so the wetting front need not advance from the inflow - a large time saving, used by the **mesh-convergence study** (`INITIAL_DEPTH`, default 0.5 m) but **not** the initial run (which the user wanted dry). `pipeline.run` records whichever file in `Artifacts.initial_conditions`. A side effect of the dry start: while the domain is mostly dry the **k-epsilon / Spalart-Allmaras turbulence linear solve** is ill-conditioned, so TELEMAC's needlessly tight default accuracy (`ACCURACY OF K`/`EPSILON`/`SPALART-ALLMARAS` = 1e-9) is unreachable within its 50-iteration cap - the transient `GRACJG: EXCEEDING MAXIMUM ITERATIONS 50` warning, which is **benign** (it reaches ~1e-6, the run stays mass-conservative and self-heals once the reach wets). `steering` therefore writes `hydrodynamics.turbulence_solver_accuracy` (default **1e-6**, plenty for turbulence) for the k-epsilon (3) / Spalart-Allmaras (6) models, which converges the turbulence solve in fewer iterations.
- Calibration CSV schema (read by HydroBayesCal): `id, x, y, z, <QTY>_DATA, <QTY>_ERROR`, where `<QTY>` is a SELAFIN name (e.g. `WATER DEPTH`, `SCALAR VELOCITY`).

v1 covers the **2D hydraulic** path end to end; the **DEM-of-Difference** (with a level of detection) is implemented in pre-processing (`dem_of_difference` config block, `dem.dem_of_difference` / `dem.resolve_lod`), and **GAIA morphodynamics** is wired for simulation - `steering.write_gaia_cas` writes a damocles-valid GAIA steering file (transport modes + bed-process capacities: morphological factor, slope effect, secondary currents, active-layer stratigraphy, prescribed solid discharges) coupled to the steady, `unsteady2d.cas` and `unsteady3d.cas` runs (`morphodynamics` config block). What **remains an extension point** is the *calibration* side: turning the DoD into per-point topographic-change calibration targets and folding the GSD `sediment_classes` into GAIA from the ground-truth template.

### Build, test, run

```bash
mamba env create -f environment.yml && mamba activate hydromate-env && pip install -e ".[dev,gui]"
hydromate cases/example-Inn/case-config.yml --check        # validate config only
hydromate cases/example-Inn/case-config.yml                # build the case
hydromate cases/example-Inn/case-config.yml --dry-run      # build, then run the solver once to validate
hydromate cases/example-Inn/case-config.yml --no-validate-env  # build without sourcing the TELEMAC env
hydromate clip <raster> -b <boundary> -o <out>   # crop one raster to a ROI, no config
hydromate rating -o <out.csv> --manning <n> --slope <S0> --width <b> --q <Q...>  # normal-flow outflow rating curve
mamba run -n hydromate-env pytest tests/ # end-to-end test on synthetic fixtures (no solver)
mamba run -n hydromate-env pytest tests/test_integration.py::<name>  # single test
mamba run -n hydromate-env ruff check src/   # lint (line-length 100)
```

Packaging is `pyproject.toml` (setuptools, `src/` layout); extras: `[dev]` = pytest+ruff, `[gui]` = streamlit. Entry points: `hydromate` (CLI) and `hydromate-gui` (Streamlit config editor - `gui/launch.py` shells out to `streamlit run gui/app.py`).

`cases/example-Inn/` holds the worked example for the Inn case, run against its `case-config.yml` as flat scripts (`mamba run -n hydromate-env python cases/example-Inn/<script>.py`). The **workflow is three ordered steps**: (1) `preprocessing.py` builds the complete TELEMAC case into `hydromate-case/simulation/` (via `pipeline.run`, at the steady discharge from **this case's** `case-config.yml` `boundaries.prescribed_flowrate` - the shared `hydromate.prepare_steady_inputs` helper reads the inflow Q and outflow-stage prescription from the config rather than a value hard-coded in the script, synthesising a constant inflow series + outflow rating only if missing) - the final mesh `geometry.slf`, `boundaries.cli`, `friction.tbl`, `steady2d.cas`, plus the HBC artifacts in `calibration-validation/`; (1b) `initial_run.py` test-runs *exactly that* `steady2d.cas` once (`hydromate.run_solver_streaming` → `TelemacRuntime.run_solver` with `-s --nozip`, no rebuild) to confirm it does not crash - the solver's listing is **streamed live** to the terminal (via `TelemacRuntime.run`'s `on_line` callback, so the run isn't silent) with a **progress bar** of simulated time vs `DURATION` (`hydromate.progress.SolverProgress`; the CFL-adaptive dt makes the *number* of steps unknown a priori, so progress is measured against the simulated-time cap `expected_duration(cfg)` = `hydrodynamics.duration` else `n_time_steps × time_step`, with the live iteration count shown). A module-level **`NCSIZE`** at the top of `initial_run.py` overrides `telemac.n_processors` for this one test run (leave it `None` to use the configured core count). The run then gets a **boundary-flux convergence analysis** (`hydromate.flux_convergence`, delegating to the user's **pythomac**) that reads the `.sortie` (needs `PRINTING CUMULATED FLOWRATES : YES`, already emitted) and writes the **same four files as pythomac's example** into `simulation/` - `extracted-fluxes.csv` + `flux-convergence.png` (per-boundary fluxes) and `convergence-rate.csv` + `convergence-rate.png` (the relative imbalance `|Q_in|-|Q_out|`/`|Q_in|` and its convergence rate). hydromate aggregates Telemac's signed per-boundary fluxes into gross in/out (so any number of liquid boundaries works), back-calculates the printout spacing from the sortie's time index (the run uses a variable dt, so `period*time_step` is wrong), writes `convergence-rate.csv` itself (pythomac only writes the `.png`), and falls back to a direct imbalance plot when the run is still filling (flat imbalance ⇒ pythomac's `logn`-based rate is all-NaN and its plot crashes). The analysis also **deletes the per-processor `*_p0000N.sortie` copies** of a parallel run (only the merged main listing matters) and detects the **absolute steady window**: when `||Q_in|-|Q_out||` stays below 1e-3 m³/s over 10 consecutive listing printouts (`flux_convergence.find_steady_window`; on a noisy steady state, whose instantaneous imbalance oscillates above that floor, the 10-printout *mean* is the fallback, flagged as such), a **`hotstart2d.cas`** is generated next to the steady case via `steering.write_hotstart_cas` - it continues from `r2d.slf` (`PREVIOUS COMPUTATION FILE`, clock reset), renames the results to `r2d-hotstart.slf` (no self-clobber), caps `DURATION` at that steady time, and keeps the constant Q/H prescriptions unchanged. This ends preprocessing; (2) `mesh_convergence_study.py` runs the grid-independence study; (3) `run_Bayes_cal.py` calibrates the built case with HydroBayesCal. An **optional 3D extension** runs after step 1b (and after step 2 fixes the horizontal mesh): `add3d.py` writes the three 3D steering files (hydrostatic flux-convergence check, non-hydrostatic steady, unsteady; see the "Optional 3D extension" section below), then `vertical_convergence_3d.py` runs the vertical-layer (`dz`) grid-independence study - see the "Optional 3D extension" section below. Step 3 compiles the FlowTracker velocity ground truth into the calibration-points CSV (the point velocity, measured at **0.6·h**, approximates the depth-averaged velocity, so it is compared to TELEMAC `SCALAR VELOCITY` = sqrt(U²+V²) built from the **horizontal** components only), ensures the `.cas` outputs `SCALAR VELOCITY` (graphic-printout `M`), emits `config_Telemac.py`, and launches HydroBayesCal's `bal_telemac.py` in its own checkout/env (`HYDROBAYESCAL_DIR` / `HYDROBAYESCAL_ENV`, defaulting to `/home/schwindt/github/hydrobayescal` and `wrr-proj`; `--prepare-only` writes the CSV+config without launching) - everything into `calibration-validation/`. HydroBayesCal reads the CSV's first four columns by position (id, x, y, z) and `<QTY>_DATA`/`<QTY>_ERROR` by name; `_ERROR` is a site-specific error in physical units added in quadrature to its built-in 10% measurement + 10% surrogate error.

### HydroBayesCal calibration (step 3) - `hydromate/bayescal.py` + `hydromate/campaigns.py`

Step 3 is **thin scripts over the package**: `run_Bayes_cal.py` (single discharge) and `run_Bayes_cal_multiflow.py` (multi discharge) each just declare the case-specific choices and call `hydromate.run_single_flow_calibration` / `hydromate.run_multiflow_calibration`. Both scripts live in `cases/case-template/` and every case folder. All logic - CSV compilation, `.cas` derivation, HBC config emission, driver staging, launching, the smoke test, resume - lives in `hydromate/bayescal.py`; the multi-campaign FlowTracker-to-CSV compilers in `hydromate/campaigns.py` (`adapter` = summary workbook + DGPS layer joined by ID; `transect` = taped cross-section + point gpkg keyed by vertical number; `inline` = inline-coordinate verticals; each keeps the 0.6-depth vertical and floors the propagated velocity error). Tests: `tests/test_campaigns.py`.

- **Single-flow** (`run_single_flow_calibration`): compiles `ground_truth.sources` into the velocity CSV, ensures the `.cas` prints `SCALAR VELOCITY` (`M`), emits `config_Telemac.py` via `calibration.emit_hbc_config`, stages `bal_telemac.py` and launches. `--prepare-only` stops before launch.
- **Multi-flow** (`run_multiflow_calibration`, `launch_mode` = `prepare`|`smoke`|`run`|`resume`): calibrates **one shared roughness against several steady discharges jointly**. The case script lists `hydromate.FlowSpec(name, discharge, kind, values, positions, duration, vel_err_floor)`. Each flow gets its own steering file derived from the built base `steady2d.cas` (only Q, the outflow stage from the synthetic rating at that Q, `DURATION`, and the results name change) and its own calibration CSV; they are joined into one 57-point (e.g.) observation/output space by the **additive hydrobayescal extension** `hydroBayesCal.telemac.multiflow_telemac.MultiflowTelemacModel` + `templates/bal_telemac_multiflow.py` (wraps one stock single-flow `TelemacModel` per flow; single-flow users untouched). `--smoke` runs an isolated 3-level tiny-run plumbing test (checks per-run JSON accumulation, that rows differ with ks, and the combined shape) in ~15 min before committing solver hours; `--resume` reuses each flow's completed initial design from `flow-<name>/.../restart_data/initial-model-outputs.json` (only_bal_mode) and skips straight to surrogate + BAL.

**Lessons baked in (all fixed / guarded):**
- **`prior_samples` is a memory trap.** gpytorch predicts the surrogate at every prior sample by building a `prior_samples x prior_samples` dense covariance **per calibration location**; 25000 OOM-kills a 16 GB box. `calibration.prior_samples` (config, default **5000**) is emitted into both single- and multi-flow configs; a low-dimensional roughness posterior needs only a few thousand. Raise only with RAM.
- **HydroBayesCal fixes (in the checkout, backward compatible for existing users):** (a) `control_telemac.rewrite_steering_file` matched only `KEYWORD = value`; hydromate `.cas` files use `KEYWORD : value`, so per-run RESULTS-FILE renames silently no-op'd - now matches `=` or `:`. (b) `function_pool.update_json_file` used `key in output_data` with **int** calibration-point IDs against JSON's **str** keys, so every run overwrote instead of appending (only run 1's outputs survived, rest read as zeros) - now `str()`-normalises keys. (c) `bal_functions.select_indexes` called `np.in1d`, **removed in NumPy 2** - now `np.isin`.
- **The staged driver extracts the `last` (converged) SELAFIN frame, not the `mean_last` window** (which would average a dry-start transient into the calibration values).
- **Data comparability governs which flows are calibratable - and verify the discharge label itself.** Compare per-campaign mean U, depth, and spatial span: a few-point survey confined to slow, shallow near-bank margins samples partially-wet cells the 2D depth-averaged model represents poorly, not the modelled channel (the Inn KB15 March-2026 campaign - 5 margin verticals, ~0.58 m / 0.02-0.52 m/s - was first excluded under a **mislabelled Q=168** that made the model look ~5x too fast; at the true **45.8 m3/s** the magnitudes match to order, but the margin points still carry the DEM too-shallow/too-fast bias and add no discharge diversity, so it stays excluded from velocity calibration). Use WATER DEPTH / flood-extent for high flow instead - **wadeable FlowTracker velocity surveys are safety-capped at low flow (~46-48 m3/s)** (river entry at high discharge endangers the operators), so velocity calibration cannot gain discharge diversity. Down-weight a single-cross-section campaign by raising its `vel_err_floor` (KB15 Nov-2025: 0.05 m/s) so its many low-variance points do not dominate the joint likelihood. `MultiflowTelemacModel` also fails fast on all-zero or all-identical initial-design rows per flow.

**Optional 3D extension (`add3d.py`, `hydromate/threed.py`).** The 3D path sits **strictly after the 2D path** and depends on it twice over: a 3D run is only built (1) once the 2D run has produced its **hotstart** result (`initial_run.py` → `r2d.slf`; the 3D case is seeded from it and would otherwise start from a dry bed), and (2) once the **2D mesh-convergence study** has settled the **horizontal** resolution - the 3D case reuses that same horizontal mesh, so building 3D before step 2 means resolving the vertical on an unvalidated horizontal grid. After `initial_run.py` has produced `r2d.slf`, `add3d.py` writes **exactly three** steering files for `telemac3d.py` next to the 2D case (no rebuild) via `threed.build_3d_cases` (which reads `r2d.slf` **once** and shares the inferred levels/turbulence/dt across all three; the per-case script is a thin wrapper printing `workflow.format_3d_cases`): (a) **`hotstart3d_hydrostatic.cas`** - `NON-HYDROSTATIC VERSION : NO` (no PPE keywords), constant in-file Q/H, `HYDROSTATIC_N_STEPS` (30k) fixed steps with `LISTING PRINTOUT PERIOD : 100` so the sortie carries enough `FLUX BOUNDARY` printouts to check when the boundary fluxes converge in a steady telemac3d run; results go to `r3d-hydrostatic.slf`/`r3d-2d-hydrostatic.slf`; (b) **`hotstart3d_hydrodyn.cas`** - the non-hydrostatic steady run with the same in-file prescribed Q (in) and H (out); (c) **`unsteady3d.cas`** - non-hydrostatic, hydrograph-driven via `unsteady.build_unsteady_3d_case(out_name=...)`: Q(t) inflow + outflow SL(t) from the **same** `inflow-hydrograph.liq` as `unsteady2d.cas` (skipped with a notice unless `boundaries.inflow` is a varying series). `--run [hydrostatic|hydrodyn|unsteady]` launches one of them streaming (default: hydrostatic). All three (and every `build_3d_cas` product) emit `PRINTING CUMULATED FLOWRATES : YES` - a valid TELEMAC-3D keyword - so pythomac can read the fluxes. Every case is **hotstarted from the 2D run**. The default hotstart is the **TELEMAC v9+ true 2D→3D continuation** (`FILE FOR 2D CONTINUATION` + `FILE FOR 2D CONTINUATION FORMAT : 'SERAFIN'` + `INITIAL TIME SET TO ZERO`), which lifts the 3D free surface + horizontal velocities from the final 2D state (in v9 this keyword alone triggers the continuation - the old `2D CONTINUATION` flag is gone). Because a thin/supercritical 2D inflow can make `telemac3d` abort with `DEBIMP_3D: PROBLEM ON BOUNDARY` on the prescribed-Q inflow, a cold-start `INITIAL CONDITIONS : 'CONSTANT DEPTH'` seed (median wetted 2D depth, which over-wets the inflow) is emitted **commented-out as a fallback** - and is the `build_3d_cas(hotstart="constant_depth")` mode the vertical convergence study uses so every per-layer run reaches steady state. `INITIAL GUESS FOR DEPTH : 1` and a `MINIMAL VALUE FOR DEPTH` floor (guards the sigma transform against dry columns) back both modes. TELEMAC-3D has **no Delft3D-style constant-dz z-layers**, only **sigma planes** (`NUMBER OF HORIZONTAL LEVELS` + `MESH TRANSFORMATION : 1`), so `infer_vertical_layers` sizes the level count from the 2D depth/cell size to target `dz ~ dx/2` while keeping `dz >= dx/4` (the "max 4× finer" rule). The turbulence model reuses the 2D `select_turbulence_model` quality check, mapped onto the 3D numbering (k-epsilon 3, Smagorinski 4, **Spalart-Allmaras 5** - 3D numbers S-A 5, not the 2D 6) with the vertical model paired per TELEMAC's rules (S-A must be 5 in both directions; k-epsilon→3; Smagorinski→vertical mixing length 2). TELEMAC-3D cannot run finite volumes (always FE), has no zonal `FRICTION DATA FILE` (a single representative `LAW OF BOTTOM FRICTION` + `FRICTION COEFFICIENT FOR THE BOTTOM` is written - **not** spatially equivalent to the 2D zonal friction), and has **no `DESIRED COURANT NUMBER`** keyword - so the fixed `TIME STEP` is sized for a target Courant of 0.6 from the 2D velocity and the cell sizes (the 2D steady run's `desired_courant` default is the safer 0.30, since its dry start is less stable than this hotstarted 3D run; raise either toward ~0.9 to march to steady state in fewer steps). It also has **no steady-state auto-stop** (the 2D `STOP IF A STEADY STATE IS REACHED` keyword does not exist in TELEMAC-3D), so the 3D run always marches the full `NUMBER OF TIME STEPS`. For wetting/drying robustness the 3D numerics use **MURD PSI advection with the locally-implicit option** for velocity *and* k-epsilon (`SCHEME FOR ADVECTION ... : 5` + `SCHEME OPTION ... : 4` - robust on tidal flats without the sub-iteration blow-up the default MURD option hits), **mass-lumping** on depth+velocity with `TREATMENT OF NEGATIVE DEPTHS : 2`, segment-wise `MATRIX STORAGE : 3`, and `ACCURACY FOR PPE : 1.E-4` (the v8.1+ default; tighter just wastes iterations on spin-up). The boundary conditions reuse the 2D `PRESCRIBED FLOWRATES`/`ELEVATIONS`/`VELOCITY PROFILES` plus a logarithmic `VELOCITY VERTICAL PROFILES`. `add3d.py --run` launches `telemac3d.py` via `run_solver_streaming(..., solver="telemac3d", duration=dt*n_steps)` (live listing + progress bar; 3D has no DURATION keyword, so the bar spans the fixed step count).

**3D vertical-layer convergence (`vertical_convergence_3d.py`, `hydromate/vertical_convergence.py`).** Choosing the number of vertical layers is a **separate discretization decision that the 2D mesh-convergence study never addresses** (step 2 only varies the horizontal cell size), so the vertical resolution `dz` needs **its own grid-independence study** - run after `add3d.py`. It is the 3D analogue of the 2D study: where the 2D study varies the horizontal cell size, this varies the **number of sigma layers** (`NUMBER OF HORIZONTAL LEVELS`) on the *same* (already 2D-converged) horizontal mesh. `run_vertical_convergence` runs the hotstarted 3D case once per layer count (a ladder around the inferred baseline, or explicit `counts=`), each in its own `postprocessing/vertical-convergence/L<n>/` folder with the geometry/`.cli` symlinked in (no mesh rebuild) and `build_3d_cas(..., n_levels=<n>)` forcing the level count (the time step adapts to the resulting `dz`), samples depth-averaged water depth + scalar velocity at the probe points from the run's `2D RESULT FILE`, and reports the relative change / observed order / GCI keyed on the layer thickness `dz` (reusing `convergence`'s report maths; the report `recommendation()` picks the **fewest grid-independent layers**). The TELEMAC run is injectable (`simulate=`) for unit tests. The whole vertical study was verified end-to-end against the real `telemac3d` solver on `ering-revised`.

**Optional unsteady extension (`unsteady_run.py`, `hydromate/unsteady.py`).** Turns the converged steady case into a **hydrograph-driven quasi-steady** run (a flood wave discretised as a sequence of steady discharges), **hotstarted from the steady result** `r2d.slf` (`PREVIOUS COMPUTATION FILE`, clock reset to zero) - so it runs strictly after step 1b. The flood wave `Q(t)` comes from **this case's** `boundaries.inflow` **time series** (a genuinely varying series; a constant Q is the steady case). Unlike the manual tutorial, hydromate **does not re-define the boundaries**: the generated `boundaries.cli` is reused unchanged (inflow `4 5 5`, outflow `5 4 4`), the inflow discharge is driven by the `LIQUID BOUNDARIES FILE` (Q(t) per inflow; SL(t) per prescribed-elevation outflow at the rating stage, else the fixed `prescribed_elevation`) and the downstream level by its prescribed elevation - **no** `5 5 5`→`4 5 5` find-replace, no separate `boundaries-unsteady.cli`, no `STAGE-DISCHARGE CURVES` keyword (that is the alternative route). The build serializes the FRONT2 liquid-boundary numbering to `liquid-boundaries.json` (via `boundary.dump_liquid_boundaries` in `pipeline.run`), so `unsteady.py` recovers the boundary order **without re-meshing**. `build_unsteady_case` writes `unsteady2d.cas` with quasi-steady numerics (`NUMBER OF CORRECTIONS OF DISTRIBUTIVE SCHEMES : 2`), a distinct `RESULTS FILE` (`r2d-unsteady.slf`, so it does not clobber its own hotstart input), and optional `CONTROL SECTIONS` (`write_control_sections` parses the `.cli`, grouping consecutive same-tag rows **by rank** into one section per open-boundary segment, endpoints = that run's first/last global node - so the run reports the flux across each boundary). `unsteady_run.py` has **in-script toggles**: `MODE_3D` (`build_unsteady_3d_case` drives the same hydrograph on the non-hydrostatic 3D mesh via `threed.build_3d_cas(unsteady=True, liquid_boundaries_file=..., duration=...)`, spanning the hydrograph by step count since 3D has no `DURATION`), and `GAIA_ENABLED` / `GAIA_BEDLOAD` / `GAIA_SUSPENDED` (fold into `morphodynamics`, adding `COUPLING WITH : 'GAIA'` + `GAIA STEERING FILE` + `COUPLING PERIOD FOR GAIA` to whichever run is built here - so **GAIA is coupled to both `unsteady2d.cas` and `unsteady3d.cas`** (and the steady case), sharing one generated GAIA `.cas`). Suspended sediment is carried as TELEMAC tracers by GAIA, needing no manual `NUMBER OF TRACERS`. `steering.write_gaia_cas` emits a **damocles-valid** GAIA steering file (verified against `gaia.dico`): it references the **same `GEOMETRY FILE` + `BOUNDARY CONDITIONS FILE`** as the coupled run (GAIA needs both even when coupled) and its results keyword is `RESULTS FILE` (**not** `GAIA RESULTS FILE`, which is not a GAIA keyword - fixed), plus `BED LOAD FOR ALL SANDS` / `SUSPENSION FOR ALL SANDS` and the bed-process capacities driven by the `morphodynamics` config block: `MORPHOLOGICAL FACTOR` (`morphological_factor`, bed-evolution acceleration over a hydrograph), `SLOPE EFFECT` + `FORMULA FOR SLOPE EFFECT` + `FRICTION ANGLE OF THE SEDIMENT` (`slope_effect`/`slope_formula`/`friction_angle`), `SECONDARY CURRENTS` + `SECONDARY CURRENTS ALPHA COEFFICIENT` (`secondary_currents`, spiral-flow bedload deviation in bends), `NUMBER OF LAYERS FOR INITIAL STRATIFICATION` + `ACTIVE LAYER THICKNESS` (`bed_layers`/`active_layer_thickness`), `PRESCRIBED SOLID DISCHARGES` (`prescribed_solid_discharges`, sediment supply per liquid boundary in FRONT2 order), `CLASSES TYPE OF SEDIMENT` (`sediment_type`), `MASS-BALANCE` and the GAIA `VARIABLES FOR GRAPHIC PRINTOUTS`. Pass `--run` to also launch the solver. The steering writers (`steering.write_cas`, `write_gaia_cas`, `threed.build_3d_cas`) are unit-tested without the solver (`tests/test_unsteady.py`).

The mesh-convergence study (`hydromate/convergence.py`, step 2; `cases/example-Inn/mesh_convergence_study.py`, which creates and works in its own `hydromate-case/mesh-convergence/` folder) runs the same steady sim on a **four-mesh r=1.3 ladder** (`ratio_levels`: one coarser x1.3, the configured baseline, two finer /1.3 and /1.3² - Celik et al. 2008 recommend a grid refinement factor **r >= 1.3**; closer-spaced grids like the old ±20% `percent_levels`, kept only for backward compat, drown the grid-to-grid differences in solver noise and degenerate the GCI denominator r^p−1) at constant discharge with TELEMAC's variable time step (per-mesh CFL dt), samples water depth + scalar velocity at the ground-truth probe points (`default_probes`), and judges convergence on the **GCI of the finest grid triplet** (observed p clamped to `THEORETICAL_ORDER` 2 for the GCI; an **asymptotic-range check** `GCI(med)/(r^p·GCI(fine)) ∈ 0.8..1.25` decides whether the GCI is trustworthy, else the finest successive relative change is the fallback - `ConvergenceReport.verdict_basis`) vs a tolerance (default **5%**, `DEFAULT_TOLERANCE`; Celik: 5-10% is engineering accuracy). Each level is built with **`mesh.size_scale`** (= level channel size / config `channel_size`), a global multiplier applied to *every* target edge length **including the per-zone `Max Edge Length (m)` gpkg values** - scaling only `channel_size`/`floodplain_size` does nothing when the gpkg carries that field (the bug that invalidated the first ering study: five "levels", one mesh). The study is **resumable** (each level folder gets a `level.json`; on re-run a prompt offers reusing completed levels, QoI re-extracted from their `r2d.slf`; size-mismatched levels re-run) and **extensible**: when not converged it offers up to `MAX_EXTRA_LEVELS` further /1.3 refinements one at a time, each prompt showing a **runtime estimate** (log-log fit of measured runtimes, theoretical t~dx⁻³ fallback) and the **mesh-validity check** of the candidate size; non-interactive sessions auto-resume and auto-stop (no hang). A refinement that **fails to mesh/run** (e.g. BAMG gives up even after its retries, or the solver diverges) is caught as the practical refinement limit: the extension stops and the report is written from the levels already completed, instead of crashing the study. **Auto-refinement mode** (`run_mesh_convergence(auto_extend=True)`, exposed by the per-case `mesh_convergence_study.py` as `python .../mesh_convergence_study.py mode='auto-refinement'`) auto-approves the resume prompt and every extension (no prompts, interactive or batch) so the study marches finer one grid at a time until it converges, exhausts `AUTO_MAX_EXTRA_LEVELS` (default 8, vs. the interactive `MAX_EXTRA_LEVELS` 3), or a level fails. Every level's report row carries the `hydromate/mesh_validity.py` checks: shear velocity from the fully-rough log law, wall **y+** (O(10⁴) in rivers, always passes - reported as standard), roughness Reynolds **ks+** (>=70 fully rough for the Nikuradse law), **dx vs ks** (dx < channel ks = roughness double-counting risk; fires first under refinement), and **turbulence-model consistency** (`steering.turbulence_pick_for_dx` vs the pinned baseline model). Every per-level build is **pre-wetted** (`INITIAL_DEPTH`, default 0.5 m -> `initialization.prewet_depth`): the channel mesh-zone nodes are hotstarted with that water depth so the solver need not advance the wetting front from a dry bed (see "Pre-wetting" below). `ConvergenceReport.to_xlsx()` writes a **styled .xlsx** (openpyxl) to `mesh-convergence/` (incl. the validity rows) and `recommendation()` picks the **coarsest grid-independent cell size** (convergence vs. compute-time tradeoff, with the runtime speed-up vs. the finest; under a GCI verdict with no rel-change-adequate level it recommends the medium grid of the converged triplet). The TELEMAC run is injectable (`simulate=`) so the report maths/xlsx are unit-tested without the solver (`tests/test_convergence.py`, `tests/test_mesh_validity.py`). Results SELAFINs are read with the minimal `selafin.read_slf` (the writer's counterpart; single/double precision, multi-frame, returns the last frame); `_geom_stats` drops the zero-length edges that merged parallel results carry at subdomain interfaces (else min-edge/dt report as 0/NaN).

A build needs a **ROI boundary polygon** (`geodata.boundary`, a closed polygon/polyline in EPSG:25832; the Inn example uses `cases/example-Inn/user-sources/geodata/roi-kb15.gpkg`) and `boundaries.liquid_boundaries` (both set in the Inn config). The steady **inflow Q comes from this case's `boundaries.prescribed_flowrate`** (m³/s) - the shared `hydromate.prepare_steady_inputs` helper (used by `preprocessing.py` and the mesh-convergence script) reads it from the config rather than a value hard-coded in any script, so each case uses its own discharge. A constant-Q `boundaries.inflow` series is then **auto-synthesised** at that discharge when missing (`boundaries.inflow` itself is optional - only a *varying* series triggers the unsteady case), and the outflow rating `boundaries.stage_discharge` is synthesised from a normal-flow curve when the `stage_discharge` outflow condition is active and none is given (the default `outflow_condition: elevation` needs no rating, just `boundaries.prescribed_elevation`), so the only machine-specific thing to set for a build is `telemac.pysource`.

## Coordinate system - non-negotiable

**Everything is EPSG:25832 (ETRS89 / UTM Zone 32N), units in metres.** This was verified for the DEMs, all shapefiles, and the gauge metadata. Any new raster, mesh, or shapefile must use the same CRS, or downstream alignment (DEM interpolation onto the mesh, breakline snapping) will silently break.

Vertical datum varies across the gauge data (DHHN12 / DHHN2016 / "m NN" vs "m NHN") - check and reconcile datum before using gauge zero-point heights as model boundary elevations.

## Data layout and meaning

The Inn co-development dataset lives under `cases/example-Inn/user-sources/geodata/` (gitignored). The exact files evolve; what `cases/example-Inn/case-config.yml` currently points at:
- `dem-2020.tif` - baseline terrain (0.5 m DEM), `geodata.dem_initial`.
- `DEM-2025-20cm.tif` - 0.20 m high-res survey, `geodata.dem_target` (enables the morphodynamic/DoD path).
- `roi-kb15.gpkg` - the ROI / max-wetted-extent polygon (`geodata.boundary`), subreach KB15.
- `liquid-boundaries.gpkg` - inflow/outflow boundary segments (drives the `.cli`).
- `mesh-zones.gpkg` - polygons with a `Zone Name` (`channel`/`floodplain`) driving the anisotropic mesh (`geodata.mesh_zones`). `channel-centerline.gpkg` - the line channel cells are elongated along (`geodata.channel_centerline`).
- `roughness-zones.gpkg` - polygons with an integer **`Zone ID`** (1 = channel, 2 = floodplain) driving the friction zonation (`geodata.roughness_zones`); `roughness-table.csv` (`zone_id,ks`, e.g. `1,0.2` / `2,0.5`) maps each id to a Nikuradse ks (`geodata.roughness_table`). `interpolate_roughness` writes these as the per-node `FRIC_ID` + `BOTTOM FRICTION` and `steering` makes the matching `.tbl` (`<id> NIKU <ks> NULL`).
- `rating-curve.csv` - outflow `Q,WSE` stage-discharge curve (`boundaries.stage_discharge`); auto-synthesised from the geodata by `preprocessing.py` if absent.
- `iws-uas/`, `flowtracker2/`, `sediment/`, `muehldorf-gauge-XS/` - ortho/UAS imagery, FlowTracker velocity ground truth, GSDs, and gauge cross-section. `cases/example-Inn/user-sources/ground-truth/` holds the calibration ground-truth spreadsheets.

`-roi-clip.tif` files are generated clip outputs (from `preprocessing.py` / `hydromate clip`), not raw inputs.

### Material / region classification (MATID scheme)

Region/zone polygons assign a max triangle area (mesh density) and a `MATID` (material zone) used later for roughness and sediment classes in GAIA. Base resolution is ~0.2 m.

| MATID | name           | max area (m²) | type        | meaning                              |
|-------|----------------|---------------|-------------|--------------------------------------|
| 1     | riverbed_fine  | 1.0           | riverbed    | fine bed (sand, silt)                |
| 2     | riverbed_coarse| 4.0           | riverbed    | coarse bed (gravel, cobbles)         |
| 3     | block_ramp     | 0.5           | block_ramp  | block ramp / high-roughness structure|
| 4     | gravel_bank    | 2.0           | gravel_bank | gravel bank / transition zone        |
| 5     | floodplain     | 25.0          | floodplain  | floodplain, vegetated overbank       |

### Boundary-condition gauge data (Bavarian LfU)

The upstream (discharge) and downstream (water level) boundaries are driven by gauge exports from the Bavarian LfU (gkd.bayern.de) - discharge [m³/s] at Kraiburg (Q ≈ 47 m³/s for the Nov-2020 reference period), stage [cm] at Wasserburg (upstream) and Mühldorf (downstream). When such CSVs are supplied via `boundaries.inflow` / `boundaries.stage_discharge`, mind the **German LfU CSV format**:
- UTF-8 **BOM** on the first line.
- **Semicolon** delimiter, **comma** decimal separator (e.g. `43,3`).
- 9 metadata lines (Quelle, station name/no., Gewässer, gauge coordinates as `Ostwert`/`Nordwert`, `Pegelnullpunktshöhe`), a blank line, then a header row (`Datum;"...[unit]";Prüfstatus`), then `"YYYY-MM-DD HH:MM";value;Geprueft` rows.
- Times are MEZ (CET). Stage is in **cm**; convert to m and add the gauge zero-point height for absolute water-surface elevation.

Read with `pandas`: `pd.read_csv(path, sep=';', decimal=',', skiprows=10, encoding='utf-8-sig')`.

### Ground-truth & calibration data (`cases/example-Inn/user-sources/ground-truth/`)

Field measurements that become **calibration targets** for HydroBayesCal, ingested by `ground_truth.py`. The canonical input is the tidy multi-tab table (below); it is authored by the user (`ground_truth.measurements`), **compiled by hydromate** from raw sources declared in `ground_truth.sources` (a list of `{category, kind, values, positions, join_key}`), or - the recommended, consistent route - compiled from the **calibration-target template** (`hydromate targets <config>` → `user-sources/ground-truth/calibration-target-data.xlsx`, referenced under `ground_truth.targets` with per-tab position layers `hydraulics_positions`/`sediment_positions`; `src/hydromate/targets.py`, tests in `tests/test_targets.py`). The template's rows are keyed by **unique IDs** joining the point gpkg/shp layers (any CRS, reprojected on ingest; explicit x/y win); its `hydraulics` tab carries u_x/u_y/u_z + fluctuations u_x'/u_y'/u_z' with auto-derived U_h/U_h'/TKE (live Excel formulas, recomputed on ingest → tidy `u_mag`/`u_mag_std`/`tke`), water depth and bottom elevation - and is populated from SonTek FlowTracker2 exports by `src/hydromate/flowtracker.py` (`read_flowtracker`/`fill_template_hydraulics`, tests in `tests/test_flowtracker.py`), auto-detecting the three real layouts (`.ft.sum`, TKE-stats, multi-sheet `FT_TKE_Summary`) keyed by each point's own ID; **the fluctuations u' are the sample standard deviation (`u std`/`Std Dev v'(x)`/σ), NOT the `VxErr` columns** (`VxErr` is the standard error of the mean ≈ std/√Npts) - where only a plain `.ft.sum` (VxErr + Npts, no std-dev) is given, u' is reconstructed as `VxErr·√Npts`; `write_target_template` drops a co-located runnable `extract_flowtracker.py` next to the xlsx that calls `fill_template_hydraulics`; its `morphodynamics` tab carries d16..d90 [mm → m] + fine fraction < 1 mm and auto-samples the **DoD raster into a per-point `dz` column** on ingest (the DoD→targets adapter); its `parameters` tab is a drop-down over `targets.PARAMETER_CATALOG` (verified TELEMAC-2D/3D/GAIA keywords: friction zones prefilled with current ks, CLASSES SHIELDS PARAMETERS, MINIMUM VALUE OF DEPTH, VELOCITY DIFFUSIVITY, secondary-currents coefficients, GAIA transport knobs, ...) with min/max test ranges + tips, ingested by `targets.read_target_parameters` and merged over `calibration.parameters` in `emit_hbc_config` (template wins; `calibration.merged_parameters`). The **hydraulics/FlowTracker path is also implemented** (`kind: flowtracker` joins `.ft.sum` values to a DGPS position layer; `kind: points` reads a layer that already carries quantities). **Still to build:** the sediment/GSD adapter into GAIA `sediment_classes` (the GSD values now land in the tidy `morphodynamics` tab but are not yet folded into the GAIA `.cas`).

**Positions vs. values are split across two folders, joined by `ID`/row order:**
- Measurement **positions** are point shapefiles under `cases/example-Inn/user-sources/geodata/` - and are in **different CRSs than the project's 25832, so they must be reprojected on ingest**:
  - `geodata/flowtracker2/dgps-flowtracker-day{1,2}_utm33.shp` - EPSG:**25833** (UTM 33N). Columns `ID, E_25833, N_25833, WaterDepth, z` (z = bed elevation). 15 points (day1) / 30 (day2).
  - `geodata/sediment/MultiPAC-Mar2020-KB15.shp` - EPSG:**32632** (WGS84/UTM 32N). `name` = Surface/Subsurface. NB its `x`/`y` *attribute* columns are swapped vs the geometry - trust the geometry.
- Measured **values** live under `cases/example-Inn/user-sources/ground-truth/`:
  - **Hydraulics - `hydraulics/FlowTracker2-KB15-day{1,2}.xlsx`**: SonTek FlowTracker2 `.ft.sum` exports for KB15. One sheet; row 0 = metadata (total `DISCHARGE` [CMS], reference gauge), row 1 = headers, row 2 = units, rows 3+ = one vertical each (joins 1:1 by `ID` to the DGPS shp). Key columns: `MeasD`/`FinalD` depth [m]; `VelX/VelY/VelZ` [m/s] (+ `VxErr/VyErr/VzErr`) → velocity components / scalar velocity.
  - **Sediment - `sediment/GSDs-Uni-Stuttgart.xlsx`**: surface & subsurface grain-size distributions (cumulative + fractional) with d65/d84; feeds GAIA `sediment_classes`.

**Target tidy model (generic, source-agnostic):** a multi-tab table - one tab per category (`hydraulics`, `sediment`, …), first 3 columns `x, y, z` (in the project CRS 25832), then quantity columns (FlowTracker hydraulics → `u, v, w, u', v', w', h`). FlowTracker is only one possible source; many ground-truth sources are conceivable, so the reader stays generic and per-source adapters feed it.

**Topographic change**: the DEM-of-Difference (`dem.dem_of_difference`, dem-2020 vs DEM-2025-20cm) is the bed-change ground truth for the GAIA / topographic-change calibration. It is produced in pre-processing when `dem_of_difference.enabled` (the `inn-2020-25` case enables it, 2020→2025), clipped to the ROI and thresholded by a **minimum level of detection** (propagated survey uncertainty `t·√(u_i²+u_t²)` or an explicit `min_lod`; sub-LoD change masked/zeroed) - see stage 1 above and the `dem_of_difference` config block. The DoD raster is **not yet** turned into per-point HydroBayesCal targets (the remaining adapter).

**xlsx gotcha:** these *FlowTracker/GSD* files break `openpyxl`'s style parser (`PatternFill ... unexpected keyword 'extLst'`), so `pandas.read_excel` fails on them on every available env. Read them by unzipping the workbook and parsing `xl/worksheets/sheet1.xml` + `xl/sharedStrings.xml` directly (the `.ft.sum` layout is stable), or with a defensive openpyxl wrapper - don't assume `read_excel` works on these inputs. (`openpyxl` itself **is** in `hydromate-env` - `convergence.ConvergenceReport.to_xlsx` uses it to *write* the styled convergence report fine; the issue is only *reading* those specific styled inputs.)

## Working conventions

- Large rasters (the DEMs/orthos run to hundreds of MB) - don't open them blindly; use `gdalinfo`/`rasterio` to read headers, and window/downsample for any processing.
- Keep raw input data immutable. Generated artifacts go under the configured phase dirs in `cases/example-Inn/hydromate-case/` (preprocessing/ simulation/ postprocessing/ mesh-convergence/ calibration-validation/), not mixed into `user-sources/`.
- This **is** a git repository (default branch `main`). Per-case `user-sources/` (input data) and `hydromate-case/` (produced artifacts) are large/local and gitignored; only the package, the case config + scripts, and docs are tracked.
