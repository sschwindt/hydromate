# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A TELEMAC hydro-morphodynamic model of a reach of the **Inn river in Bavaria, Germany**. The goal is a 2D depth-averaged hydraulic + sediment-transport simulation (TELEMAC-2D coupled with GAIA), set up automatically and calibrated with quantified uncertainty via [HydroBayesCal](https://github.com/Ecohydraulics/hydrobayescal).

**Overarching aim:** largely automate *both* sides of the workflow around HydroBayesCal - **pre-processing** (geodata → ready TELEMAC case) and **post-processing** (field **ground-truth** → calibration targets + result extraction). Pre-processing (stages 1–5) is built for the 2D hydraulic path; the **post-processing / ground-truth ingestion is the active frontier** (turning FlowTracker velocity/depth, grain-size distributions, and DEM-of-Difference topographic change into the calibration-points CSV and GAIA inputs HydroBayesCal consumes). See "Ground-truth & calibration data" below.

The tracked repository is the **`hydromate` package** (`src/hydromate/`) plus a data-free **`cases/case-template/`** scaffold (config + the workflow scripts `preprocessing.py` / `initial_run.py` / `mesh_convergence_study.py` / `run_Bayes_cal.py` and the multi-discharge variant `run_Bayes_cal_multiflow.py`, the optional 3D extension `add3d.py` / `vertical_convergence_3d.py`, and the optional unsteady extension `unsteady_run.py` + `USAGE.info` + `user-sources/README.md`, the starting point for a new case) and the worked example case under `cases/example-Inn/` (its `case-config.yml`, `preprocessing.py`, `initial_run.py`, `mesh_convergence_study.py`, `add3d.py`, `vertical_convergence_3d.py`, `run_Bayes_cal.py`). Each case lives in `cases/<name>/` and keeps only those tracked files; the real Inn **input data** (DEMs, orthos, zone GeoPackages, gauge data, ground truth) is large (~5 GB) and lives in `cases/example-Inn/user-sources/` for co-development only, while produced artifacts land in `cases/example-Inn/hydromate-case/`, split by workflow phase: `preprocessing/` (DEM clips, meshes, ground-truth table), `simulation/` (the TELEMAC case build + results, incl. the 3D `<case>3d.cas`), `postprocessing/` (general post-processing, plus `mesh-convergence/` grid-independence and `vertical-convergence/` 3D layer studies), `calibration-validation/` (HydroBayesCal artifacts). Each phase's script writes its outputs and its `hydromate.log` into its own subfolder. Both `user-sources/` and `hydromate-case/` are **gitignored** (`.gitignore` ignores `cases/*/user-sources/` and `cases/*/hydromate-case/`, plus a safety net of binary/geo extensions `*.tif/*.gpkg/*.shp/*.xlsx/*.slf/*.log/...`); a CI workflow (`.github/workflows/file-size-limit.yml`) additionally fails any push/PR with a tracked file over 20 MB. Don't assume the data files are present in a fresh checkout. See `README.md` for the workflow and `cases/example-Inn/case-config.yml` for the case config (a commented template; all paths resolve relative to the config file's directory).

## The `hydromate` workflow

`hydromate cases/example-Inn/case-config.yml` runs a 5-stage pipeline (`src/hydromate/pipeline.py`):

1. `dem.py` - reproject + clip the initial (and optional target) DEM to the ROI boundary. When `dem_of_difference.enabled` (or `morphodynamics.enabled`), also computes the **DEM-of-Difference** (`dem.dem_of_difference`, `dem_target - dem_initial` on the ROI-clipped initial grid) thresholded by a **minimum level of detection** (`dem.resolve_lod`): an explicit `dem_of_difference.min_lod`, else the propagated survey uncertainty `t·√(uncertainty_initial² + uncertainty_target²)` (`dem.propagated_lod`, `t` from `confidence_level`); sub-LoD cells are masked to nodata (`mask_below_lod`) or zeroed, and the net/erosion/deposition volumes are logged. A precomputed `geodata.dem_of_difference` short-circuits the computation.
2. `mesh.py` + `selafin.py` - gmsh triangular mesh; DEM interpolated onto nodes; geometry written as SELAFIN with a `FRIC_ID` per-node variable (so no separate ZONES FILE is needed). The geometry is written in **double precision** (SERAFIND); single precision collapses sub-metre cells on UTM coordinates (see `selafin.py` design point). `build_mesh` prunes gmsh's geometry/1D-only nodes to triangle-referenced nodes (no orphans/duplicates), enforces consistent CCW winding, then runs `mesh_quality.assess_quality` (logged via `log_report`, stored on `Mesh.quality`). The mesh boundary is walked to build IPOBO, which **must** stay consistent with the `.cli` row order. **Two meshing strategies** (auto-selected): *anisotropic* (when `geodata.mesh_zones` + `geodata.channel_centerline` are set) types each mesh-zone polygon `channel`/`floodplain`/`refinement` (by `Zone Name` substring) and sizes it by its own `Max Edge Length (m)` field - channel cells elongated along the centerline, floodplain/refinement near-equilateral - via a metric-tensor background view + gmsh **BAMG** (`Mesh.Algorithm=7`); *isotropic fallback* uses `default_size`/`breakline_size`/`region_sizes` distance fields. See "Meshing" below.
3. `boundary.py` - classify contour nodes against the liquid-boundary lines and write the `.cli`. The lines come from `boundaries.liquid_boundaries` (a line layer whose `Type (inflow/outflow)` field - note the Inn file's typo `Type (inflow/outlfow)`, still detected - tags each line `inflow`/`outflow`; several of each allowed) and must coincide with the mesh-zone outer bounds. Codes: solid wall `2 2 2` (every non-liquid outer node), inflow `4 5 5` (prescribed Q, depth free - `LIHBOR` must be 4 not 5, else the inflow depth is forced to the inflow's PRESCRIBED ELEVATIONS slot of 0 and TELEMAC's DEBIMP aborts on a dry inflow), outflow `5 4 4` prescribed-elevation (the default `boundaries.outflow_condition: elevation`, a fixed WSE from `boundaries.prescribed_elevation`; or `stage_discharge` for a WSE from the rating curve at the simulated Q) or `4 4 4` free/Neumann (`outflow_condition: free`, needs no WSE). Matching tolerance is tied to the local edge length (anisotropic: ~2×`floodplain_size`). If total inflow- vs outflow-node counts differ by >10%, a stability-risk warning is logged.
4. `steering.py` - friction `.tbl` (one row per friction zone: `<id> <LAW> <coef> NULL`, ends with `END`; comments only on `*` lines - rows come from `friction.zones`/MATID or, failing that, the roughness table as `<Zone ID> NIKU <ks> NULL`) and the Telemac2d `.cas`; GAIA `.cas` when enabled. The **default solver is the classic finite-element kernel** (`hydrodynamics.finite_volumes: false`); set it true for the HLLC finite-volume kernel (robust on transcritical wetting/drying but constant-viscosity only). The **turbulence model is auto-selected** (`hydrodynamics.turbulence_model: auto`) by `steering.select_turbulence_model(cfg, mesh)` from the channel cell size relative to the turbulence length scale (the flow depth) and the velocity guess `initial_velocity_guess` (U≈1 m/s): **Smagorinski LES (4)** when the mesh resolves ≥80% of the TKE (`dx/L ≤ 0.2^1.5`, ~11+ cells/L - the LES validity gate), **k-epsilon (3)** at moderate resolution (≥~4 cells/L), **Spalart-Allmaras (6)** on coarse meshes; an explicit int/name overrides, and finite volumes force model 1. The **initial run is always steady** (`steady2d.cas`). The FE numerics are written **compute-stable by default** to keep the wetting/drying steady march from exploding: `time_step` is only a conservative CFL **start** step (0.25 s) while `desired_courant` (0.30) drives the adaptive marching step, `IMPLICITATION FOR DEPTH/VELOCITY` 0.80 (config `implicitation`), `FREE SURFACE GRADIENT COMPATIBILITY` 0.9, `DISCRETIZATIONS IN SPACE : 11;11` (linear FE, required by the distributive advection scheme 14), `NUMBER OF SUB-ITERATIONS FOR NON-LINEARITIES`/`MAXIMUM NUMBER OF ITERATIONS FOR ADVECTION SCHEMES`, `H CLIPPING : NO`, and a raised k-epsilon solve budget (`MAXIMUM NUMBER OF ITERATIONS FOR K AND EPSILON`, config `max_keps_iterations`). The graphic printout is `'U,V,S,B,H,M,Q,F'` plus `K,E` (TKE + dissipation) **for the k-epsilon model (3)**. **Time bound:** with the default `variable_timestep` the run is capped by `DURATION` (the explicit `hydrodynamics.duration` in seconds, else the `n_time_steps × time_step` fallback - so a small CFL start step no longer shrinks the simulated time), **not** `NUMBER OF TIME STEPS` - the latter does **not** terminate a variable-dt run (the CFL-driven dt is unknown a priori), so it would otherwise be unbounded. Convergence is judged by the **boundary-flux balance** (`initial_run.py` → `hydromate.flux_convergence`), not by the solver. **The steady-state auto-stop is OFF by default** (`hydrodynamics.stop_if_steady: false`) and is hard-suppressed whenever `variable_timestep` is on: TELEMAC's `steady.f` stops when the change between **two consecutive time steps** falls below `STOP CRITERIA`, but that is an **absolute per-step** change (order **H ; (U,V) ; tracers** in `steady.f`; the dico's English help listing (U,V) first is wrong), and with the tiny CFL dt it false-fires during a slow transient (e.g. a low-Q reach still filling from a dry start) **long before the fluxes balance** - the run halts far from steady state (the symptom: it stops with inflow ≠ outflow). It is emitted only for a steady **fixed-step** run (`variable_timestep: false`, where a per-step change is meaningful), never for the unsteady run, and **TELEMAC-3D has no equivalent keyword**. When `boundaries.inflow` carries a *varying* hydrograph, `pipeline.run` additionally writes `unsteady2d.cas` (DURATION from the series) plus a TELEMAC liquid-boundaries file (`inflow-hydrograph.liq`, `Q(t)` per inflow / `SL(t)` per prescribed-elevation outflow via `steering.write_liquid_boundaries`). The steady inflow Q comes from `boundaries.prescribed_flowrate` (the optional `boundaries.inflow` series, read by `hydraulics.py`, is only for a varying hydrograph / unsteady case). The outflow water-surface elevation is needed for the prescribed-elevation conditions: the default `boundaries.outflow_condition: elevation` uses `boundaries.prescribed_elevation`, while `stage_discharge` interpolates `boundaries.stage_discharge` (a Q-h CSV; one pair suffices for steady) at the simulated Q; `free` prescribes nothing. When no measured rating curve exists, `hydromate.rating.generate_stage_discharge` (CLI: `hydromate rating`) synthesises one from a Manning `n`/Strickler `Kst` and a trapezoidal channel geometry by inverting Manning's normal-flow equation; `rating.synthesize_outflow_rating(cfg, Q)` derives the geometry from the case data (width = outflow liquid-boundary line length, bed = DEM thalweg along it, slope = reach slope from the DEM along the centerline, roughness = `friction.boundary_*`) and `cases/example-Inn/preprocessing.py` (and the convergence-study script) call it to auto-generate `boundaries.stage_discharge` when missing. The lateral-boundary friction keywords (`LAW OF FRICTION ON LATERAL BOUNDARIES` / `ROUGHNESS COEFFICIENT OF BOUNDARIES`) come from `friction.boundary_law` / `boundary_coefficient` (Inn: Strickler 38).
5. `ground_truth.py` + `calibration.py` - compile the configured `ground_truth.sources` into the **tidy multi-tab table** (`ground_truth.compile_ground_truth`, written to `preprocessing_dir/ground-truth.xlsx` unless `ground_truth.measurements` overrides), then turn it into `measurements-calibration.csv` and the HydroBayesCal `config_Telemac.py` (both in `calibration_dir` = `calibration-validation/`).

`pipeline.run()` returns an `Artifacts` dataclass listing every produced path; `cli.py` logs these. The package's public API (`hydromate/__init__.py`) exports `Config`, `load_config`, `clip_to_roi`, `clip_dem_to_roi`, the DoD helpers `dem_of_difference` / `propagated_lod` / `resolve_lod`, `compile_ground_truth`, `read_tidy`, the mesh helpers `build_mesh` / `channel_node_mask` / `interpolate_elevations` / `interpolate_roughness` / `write_mesh` / `assess_quality`, the rating-curve helpers `generate_stage_discharge` / `normal_depth` / `stage_for_discharge` / `synthesize_outflow_rating`, the wetted-extent diagnostics `wetting_report` / `outlet_profile` (`hydromate/wetting.py`), the water-table helpers `fit_phreatic_plane` / `water_table_depth` / `patch_node_mask` / `PhreaticPlane` (`hydromate/watertable.py`), the turbulence helpers `select_turbulence_model` / `eddy_viscosity_estimate`, the TELEMAC-3D helpers `build_3d_cas` / `infer_vertical_layers` / `select_3d_turbulence` / `run_vertical_convergence` / `layer_levels`, the mesh-convergence helpers `run_mesh_convergence` / `percent_levels`, the shared per-case workflow helpers `prepare_steady_inputs` / `resolve_discharge` / `synthesize_constant_inflow` / `synthesize_rating_if_missing` / `format_flux_convergence` / `report_wetting` / `report_sections` / `mesh_from_geometry` / `water_table_mask` / `run_solver_streaming` / `expected_duration` (`hydromate/workflow.py` - the logic the per-case `preprocessing.py` / `initial_run.py` / `mesh_convergence_study.py` scripts share, so they stay thin), the live solver-progress renderer `SolverProgress` (`hydromate/progress.py`), and the logging helpers `setup_logging` / `log_step` / `logging_to`. `mesh.build_mesh(cfg)` (no DEM) yields a bare mesh; `interpolate_elevations(mesh, dem, decimals=4)` fills the bottom from a raster (rounded); `write_mesh(mesh, path)` writes a geometry SELAFIN. These low-level helpers let you build a mesh programmatically; the worked example's `preprocessing.py` instead drives the full `pipeline.run` build (writing `geometry.slf` etc. into `simulation/`; see the workflow below).

### Meshing (stage 2)

The mesher is **gmsh**, chosen over the SALOME/Q4TS route (which the working Inn model historically used) because gmsh is pip-installable, fully headless/scriptable, and supports the anisotropic meshing needed here - whereas Q4TS runs inside SALOME's GUI/SMESH stack and is heavyweight/version-sensitive to automate. SALOME lives at `/home/schwindt/opt/salome/` if ever needed.

- **Anisotropic, flow-aligned channel** (the requirement): channel triangles are *elongated along the channel centerline*, floodplain triangles near-equilateral, with a smooth transition. Implemented exactly like gmsh tutorial **t17**: build a coarse background triangulation (a Delaunay grid over the ROI bbox, node-budget-capped ~40k so any domain fits in memory), assign each background node a **3×3 metric tensor** (eigenvalue = 1/h²; anisotropic `1/(channel_size·anisotropy)²` along the local centerline tangent and `1/channel_size²` across, inside `channel` zones; isotropic `1/floodplain_size²` elsewhere), push it as a `TT` list **PostView** + `setAsBackgroundMesh`, then mesh with **`Mesh.Algorithm=7` (BAMG)**, `Mesh.SmoothRatio=growth_ratio`, `Mesh.AnisoMax`. The coarse background also produces the smooth channel→floodplain blend (gmsh interpolates the metric within each background triangle).
- Zone selection is by **substring** of the `Zone Name` attribute (case-insensitive): `*channel*` vs `*floodplain*` in `geodata.mesh_zones`. The centerline (`geodata.channel_centerline`) is sampled and `np.gradient` gives per-vertex tangents (nearest via `cKDTree`).
- BAMG **approximates** the metric: realised cross-channel size and anisotropy come out a bit gentler than the configured targets, and `growth_ratio` (default 1.2) intentionally relaxes them near banks. Knobs: `mesh.channel_size` 0.5, `floodplain_size` 1.5, `growth_ratio` 1.2, `channel_anisotropy` 4.0, `max_aspect_ratio` 4.0. Defaults are **high-res**: the Inn KB15 ROI (~0.32 km², ~130 m-wide channel) yields ~720k elements / ~360k nodes (~90 s, ~0.7 GB; the aspect cap below tightens `AnisoMax` which refines the mesh) - raise the sizes while iterating.
- **Aspect-ratio cap** (`mesh.max_aspect_ratio`, default 4.0 = longest:shortest edge): BAMG overshoots the metric anisotropy in the tail (~1.6x) and leaves a few channel slivers, so `Mesh.AnisoMax` is set to `max_aspect_ratio/1.6` and a post-mesh **edge-flip** pass (`_flip_sharp_edges`) flips the shared (long) edge of over-sharp cell pairs - a topological repair that touches only the offending cells (boundary untouched, IPOBO/winding preserved, no inversions), bringing the realised channel max from ~6.5:1 down to ≤~4:1 while keeping the bulk elongation (channel aspect median ~2.0 vs floodplain ~1.4).
- **The anisotropic mesh is NOT reproducible run to run** - a measured property, not a suspicion. Building the isar-2025 mesh twice from identical inputs **inside one process** gives 230,286 vs 231,223 nodes (458,769 vs 460,654 elements, 1801 vs 1790 boundary nodes; ~0.4% spread, min edge 0.191 vs 0.194 m). The cause is the retry below: **BAMG fails intermittently on the first attempt** with the same inputs, and the retry ladder then meshes with a coarser background metric grid, giving a different but equally valid mesh. gmsh is already single-threaded (`General.NumThreads` = 1), so this is not thread scheduling. Consequences worth knowing: `geometry.slf` / `boundaries.cli` / `initial-conditions.slf` **cannot be byte-compared** between runs (regression-test them on mesh *statistics* within ~1% instead); a **resumed mesh-convergence study may compare levels built at different retry rungs**, so a level re-run is not guaranteed to reproduce its own earlier mesh; and a published result should quote the `geometry.slf` actually used rather than assume it can be regenerated bit-for-bit. The OpenFOAM mesh has no such problem - it is hydromate's own structured lattice and *is* bit-reproducible.
- **BAMG failure retry** (`build_mesh`, `_BAMG_RETRY_LADDER`): at fine, high-contrast anisotropic metrics (e.g. a small `refinement` zone next to a coarser floodplain, hit as the mesh-convergence study refines) BAMG's Delaunay insertion can abort with `Fatal error in the meshgenerator 1001 / BAMG failed`. Empirically a **coarser** background metric grid rescues it (larger background triangles smooth the interpolated size gradient BAMG must honour; a *denser* grid makes it worse), as does a looser `Mesh.AnisoMax`. `build_mesh` therefore retries `gmsh.model.mesh.generate(2)` on a BAMG failure with a ladder of `(background node budget, AnisoMax relaxation)` each gentler than the last (`(40000,1.0) -> (20000,1.0) -> (10000,1.5) -> (6000,2.5)`) before re-raising; the normal path meshes on the first (default) attempt with no retry. Isotropic meshing has a single attempt.
- The **isotropic fallback** (no mesh_zones/centerline) is the original distance-field path (`default_size`/`breakline_size`/`region_sizes`); the integration test exercises it.
- **Quality assessment** (`mesh_quality.py`, vectorised, scales to the ~525k-element mesh): logs per-region (channel vs floodplain, via a centroid-in-`_channel_union` mask) internal angles, aspect ratio, skewness; the **shortest edge** (flagged as CRITICAL for the CFL-limited adaptive time step); and the fraction of adjacent-cell area jumps over `mesh.max_area_jump` (20%). The channel is `relaxed=True` so its *intended* anisotropy (aspect ≫ 1) is reported but never warned on - shape warnings (angle < `min_angle_deg`/> `max_angle_deg`, high aspect) apply to the floodplain only. Fatal defects (zero-area, inverted/mixed-orientation, duplicate nodes, non-manifold edges) **raise**; orphan nodes, extra boundary loops (hanging gaps) and IPOBO mismatch (wrong boundary tags) warn. Thresholds are `mesh.min_angle_deg`/`max_angle_deg`/`max_area_jump`.
- Meshing (mesh-zones) and friction (roughness-zones) are **separate concerns**: `geodata.mesh_zones` only sizes the mesh. Friction zonation comes from `geodata.roughness_zones` (an integer `Zone ID` per polygon): `mesh.interpolate_roughness(cfg, mesh)` tags every node/element with the `Zone ID` it falls in (nearest polygon otherwise), writes it as the per-node `FRIC_ID` (overriding the MATID-derived ids), and stores the `roughness_table` value for that id as the `BOTTOM FRICTION` variable. `mesh.run` (hence `pipeline.run`) calls it whenever `roughness_zones` + `roughness_table` are set, so the built `geometry.slf` carries the zone `FRIC_ID` + `BOTTOM FRICTION`, and `steering.write_friction_tbl` derives the matching `.tbl` rows (`<Zone ID> NIKU <ks> NULL`, law `friction.roughness_law`, default 5) from the same table. HydroBayesCal perturbs each `ks` via `zone1`/`zone2`.

Key design points:
- The build runs in its **own** `hydromate-env` conda env (gmsh/geopandas/rasterio); it does not import TELEMAC's Python. `env.py` *sources* `telemac.pysource` (the `pysource.*.sh`) in a subshell for any solver/SELAFIN call. The config's `telemac.pysource` must point at the real script (e.g. `/home/schwindt/opt/telemac/configs/pysource.mint22.sh`).
- Friction zonation has two routes: (a) the **roughness-zones** route - `geodata.roughness_zones` (`Zone ID`) + `geodata.roughness_table` (id→ks) drive the per-node `FRIC_ID` and `BOTTOM FRICTION` via `interpolate_roughness` (preferred for the Inn case; see the Meshing section); (b) the older **MATID** scheme (1 riverbed_fine … 5 floodplain; see table below) carried by `geodata.region_points` + `geodata.region_table` and/or `friction.zones` in the config → friction `.tbl` rows and `zone<MATID>` calibration parameters. Either way HydroBayesCal perturbs the coefficient column of the `.tbl`. `steering.write_friction_tbl` builds the `.tbl` in priority order: explicit `friction.zones` (MATID) > the roughness table (one `<Zone ID> NIKU <ks> NULL` row each) > a single default zone - so the `.tbl` rows always match the geometry's per-node `FRIC_ID`.
- `src/hydromate/selafin.py` is a self-contained big-endian SELAFIN writer (plus a `read_slf` reader for results); its output is validated against TELEMAC's own `data_manip.formats.selafin.Selafin` reader in the tests.
- **Logging** (`src/hydromate/logsetup.py`): each script/phase writes a compound, timestamped `hydromate.log` into its **own output folder** (`setup_logging(path)` routes the `hydromate` logger and captured Python warnings to it; file at DEBUG, console at the chosen level, append mode). the build (`pipeline.run`, called by `preprocessing.py`; and `initial_run.py`'s test run) -> `model_dir` (`simulation/`), the mesh-convergence study -> `mesh-convergence/` (scoped via the `logging_to(path)` context manager so it doesn't capture the per-level builds elsewhere). `log_step(name)` logs `START`/`DONE … in N.NNs` (or `FAILED … after N.NNs`) - wrapped around every pipeline stage and the heavy mesh/convergence sub-steps for per-step timing. `pipeline.run(..., log_to_file=False)` skips its own logfile (the convergence study's per-level builds use this so they log only to `mesh-convergence/hydromate.log`). Tests reset handlers via an autouse fixture (`tests/conftest.py`).
- **Initial condition - DRY START (default) vs pre-wetting**: the initial run is a **dry start** by default. A *fully* dry bed (`ZERO DEPTH`) can't be used because TELEMAC's `DEBIMP` aborts at a prescribed-Q inflow when the inflow cross-section is dry (it scales the velocity profile by Q/Q1 with Q1 ∝ ∫H along the inflow; H=0 ⇒ Q1=0 ⇒ abort, even with the correct `4 5 5` code - see the inflow-cli memory). So `steering.write_dry_start_conditions` seeds a thin water **plug only on the nodes within `initialization.dry_start_extent` of the inflow line(s)** (default ~5 cells) to `dry_start_depth` (default 0.5 m, kept ≥ normal depth so the inflow stays subcritical) and leaves the rest of the domain **dry**; the `.cas` continues from this SELAFIN (`PREVIOUS COMPUTATION FILE` + `INITIAL TIME SET TO ZERO : YES`) and the flow wets the reach from the inflow. The inflow geometry comes from `boundary._load_liquid_lines`; with no inflow line it falls back to the analytical dry `INITIAL CONDITIONS`. **Pre-wetting** (`initialization.prewet_depth`, m) is the *alternative*: when set, stage 4 instead hotstarts the **`*channel*` mesh-zone** (`write_initial_conditions` + `mesh.channel_node_mask`) so the wetting front need not advance from the inflow - a large time saving, used by the **mesh-convergence study** (`INITIAL_DEPTH`, default 0.5 m) but **not** the initial run (which the user wanted dry). **How the seeded surface is built** is `initialization.prewet_mode`: the default **`normal-depth`** (`_normal_depth_prewet_depth`) cuts a real perpendicular cross-section every `prewet_bin_spacing` (20 m) along the centerline, samples it at 0.5 m, clips it to the channel zones, and seeds the **stage that conveys the case discharge** through it via `rating.stage_for_discharge` (the Keulegan conveyance inversion factored out of `section_rating`, so the seed and the outflow rating share one implementation), with the local bed slope from the gradient of the transect thalwegs rather than one reach slope. The seeded surface is `thalweg + prewet_fill x (normal stage - thalweg)`; **`prewet_fill` is 0.70, below 1 on purpose** - under-seeding is recoverable (the flow refills a pool in seconds), over-seeding is not, because a 2D model has neither infiltration nor evaporation and water perched above the converged surface becomes permanent stagnant film. `prewet_mode: constant` is the older `_longitudinal_prewet_depth` (a low bed percentile per bin + `prewet_depth`), also the automatic fallback without a centerline or a discharge; on the braided isar-2025 reach it seeded a median **0.28 m above** the converged surface and left 4694 m2 (35% of the wetted area) as film that had stopped draining. `prewet_min_depth` (0.05 m) additionally leaves a node dry rather than laying down a feathered margin (a seed film is exactly what stalls), and `drainable_prewet` still runs on top. **After every filter the inflow plug is re-imposed** (`_inflow_plug_mask`, same `dry_start_extent`/`dry_start_depth` as the dry start): none of the filters has any reason to keep the inflow cross-section wet, and the normal-depth seed is shallowest exactly at the upstream end, so without the guard `DEBIMP` aborts the run at t=0 on a dry inflow - which is precisely what the old over-seeding had been hiding. Sizes are validated in `tests/test_prewet.py`; the calibration is recorded in `cases/isar-2025/test-approaches.md` (R2). `pipeline.run` records whichever file in `Artifacts.initial_conditions`. A side effect of the dry start: while the domain is mostly dry the **k-epsilon / Spalart-Allmaras turbulence linear solve** is ill-conditioned, so TELEMAC's needlessly tight default accuracy (`ACCURACY OF K`/`EPSILON`/`SPALART-ALLMARAS` = 1e-9) is unreachable within its 50-iteration cap - the transient `GRACJG: EXCEEDING MAXIMUM ITERATIONS 50` warning, which is **benign** (it reaches ~1e-6, the run stays mass-conservative and self-heals once the reach wets). `steering` therefore writes `hydrodynamics.turbulence_solver_accuracy` (default **1e-6**, plenty for turbulence) for the k-epsilon (3) / Spalart-Allmaras (6) models, which converges the turbulence solve in fewer iterations.
- Calibration CSV schema (read by HydroBayesCal): `id, x, y, z, <QTY>_DATA, <QTY>_ERROR`, where `<QTY>` is a SELAFIN name (e.g. `WATER DEPTH`, `SCALAR VELOCITY`).

v1 covers the **2D hydraulic** path end to end; the **DEM-of-Difference** (with a level of detection) is implemented in pre-processing (`dem_of_difference` config block, `dem.dem_of_difference` / `dem.resolve_lod`), and **GAIA morphodynamics** is wired for simulation - `steering.write_gaia_cas` writes a damocles-valid GAIA steering file (transport modes + bed-process capacities: morphological factor, slope effect, secondary currents, active-layer stratigraphy, prescribed solid discharges) coupled to the steady, `unsteady2d.cas` and `unsteady3d.cas` runs (`morphodynamics` config block). What **remains an extension point** is the *calibration* side: turning the DoD into per-point topographic-change calibration targets and folding the GSD `sediment_classes` into GAIA from the ground-truth template.

Packaging is `pyproject.toml` (setuptools, `src/` layout); extras: `[dev]` = pytest+ruff, `[gui]` = streamlit. Entry points: `hydromate` (CLI) and `hydromate-gui` (Streamlit config editor - `gui/launch.py` shells out to `streamlit run gui/app.py`).

`cases/example-Inn/` holds the worked example for the Inn case, run against its `case-config.yml` as flat scripts (`mamba run -n hydromate-env python cases/example-Inn/<script>.py`). The **workflow is three ordered steps**: (1) `preprocessing.py` builds the complete TELEMAC case into `hydromate-case/simulation/` (via `pipeline.run`, at the steady discharge from **this case's** `case-config.yml` `boundaries.prescribed_flowrate` - the shared `hydromate.prepare_steady_inputs` helper reads the inflow Q and outflow-stage prescription from the config rather than a value hard-coded in the script, synthesising a constant inflow series + outflow rating only if missing) - the final mesh `geometry.slf`, `boundaries.cli`, `friction.tbl`, `steady2d.cas`, plus the HBC artifacts in `calibration-validation/`; (1b) `initial_run.py` test-runs *exactly that* `steady2d.cas` once (`hydromate.run_solver_streaming` → `TelemacRuntime.run_solver` with `-s --nozip`, no rebuild) to confirm it does not crash - the solver's listing is **streamed live** to the terminal (via `TelemacRuntime.run`'s `on_line` callback, so the run isn't silent) with a **progress bar** of simulated time vs `DURATION` (`hydromate.progress.SolverProgress`; the CFL-adaptive dt makes the *number* of steps unknown a priori, so progress is measured against the simulated-time cap `expected_duration(cfg)` = `hydrodynamics.duration` else `n_time_steps × time_step`, with the live iteration count shown). A module-level **`NCSIZE`** at the top of `initial_run.py` overrides `telemac.n_processors` for this one test run (leave it `None` to use the configured core count). The run then gets a **boundary-flux convergence analysis** (`hydromate.flux_convergence`) that reads the `.sortie` (needs `PRINTING CUMULATED FLOWRATES : YES`, already emitted) and writes four files into `simulation/` - `extracted-fluxes.csv` + `flux-convergence.png` (per-boundary fluxes) and `convergence-rate.csv` + `convergence-rate.png` (the relative imbalance `|Q_in|-|Q_out|`/`|Q_in|` and its convergence rate). The listing is parsed by **`hydromate.sortie`** (`read_sortie` / `latest_sortie`): each `BALANCE OF WATER VOLUME` block is read as a unit and its time taken from the `RELATIVE ERROR IN VOLUME AT T =` line *inside* it, so times, volumes and fluxes cannot drift out of alignment and no sample is fabricated. This replaced a dependency on the external **pythomac** package, which cannot be vendored (it is GPL-3 and its parser derives from TELEMAC's GPL-3 `postel`, while hydromate is BSD-3) and whose package boundary forced several adapters: the printout spacing had to be back-calculated (a CFL-adaptive run has no fixed `period*time_step`), `convergence-rate.csv` had to be written separately (only the `.png` was produced), and the rate plot had to be swapped out whenever the rate was undefined. Now `flux_convergence` owns the maths (`relative_imbalance`, `convergence_rate`, `convergence_index`) and both plots; the converged time and iteration count are read straight off the listing rather than estimated, and the convergence figure always shows the relative imbalance (with the tolerance marked) plus the rate where it is defined - during the filling phase the rate is undefined everywhere, which is exactly when one needs to see the imbalance. **Tolerance grades** (`hydrodynamics.flux_tolerance`, default **1e-3**): the imbalance is *relative*, so the discharge/depth/velocity read off a steady run inherit it directly - 0.1% is far inside field-measurement uncertainty and inside the 5% the mesh-convergence study accepts, so 1e-3 is the right grade for a hydraulic result. The stricter **1e-4** (`HOTSTART_TOLERANCE`) is for a **hotstart seed**, where the residual transient is inherited by every perturbed calibration run rather than averaged out; 1e-6 is a rarely-worth-it validation grade. The *absolute* steady criterion is derived as `flux_tolerance x prescribed_flowrate` (so the hotstart gate means the same on a 2 m3/s side channel as on a 200 m3/s river) rather than a fixed 1e-3 m3/s. The analysis also **deletes the per-processor `*_p0000N.sortie` copies** of a parallel run (only the merged main listing matters) and detects the **absolute steady window**: when `||Q_in|-|Q_out||` stays below 1e-3 m³/s over 10 consecutive listing printouts (`flux_convergence.find_steady_window`; on a noisy steady state, whose instantaneous imbalance oscillates above that floor, the 10-printout *mean* is the fallback, flagged as such), a **`hotstart2d.cas`** is generated next to the steady case via `steering.write_hotstart_cas` - it continues from `r2d.slf` (`PREVIOUS COMPUTATION FILE`, clock reset), renames the results to `r2d-hotstart.slf` (no self-clobber), caps `DURATION` at that steady time, and keeps the constant Q/H prescriptions unchanged. A balanced flux budget says nothing about **where** the water is, so `initial_run.py` additionally writes `wetting-report.csv` and `outlet-profile.csv` via **`hydromate.wetting`**: `wetting_report` splits the wetted area into *active* flow (H > 0.05 m, |U| > 0.15 m/s, in the largest connected body), *stagnant film* (wet but under 0.05 m/s) and *isolated puddles*, attributes each to the pre-wet seed when the initial-conditions SELAFIN is passed, and samples earlier frames to say whether the film is still draining or has **plateaued** - the failure mode a longer run cannot fix, since a 2D model has neither infiltration nor evaporation (isar-2025: 4694 m2 of film, 75% seeded, shrinking 1.8% over 3100 s). `outlet_profile` bands the actively flowing nodes by distance from the outflow line, reports the discharge-weighted free surface / depth / Froude per band, and compares the near-boundary surface slope with the reach's own to return `backwater` (the prescribed stage is holding the level up over ground that should be dry) / `drawdown` / `neutral`. The report's wetted threshold is `hydrodynamics.wet_depth` (0.01 m) - a **reporting** convention, since on a bed with ks 0.05-0.5 m water 5 mm deep stands *inside* the grain roughness rather than flowing over it (on isar-2025 that band was 13% of the wetted area but 0.16% of the volume); use the same filter in ParaView so the picture and the report agree. Water an external source holds in place is passed in via `supported=` and reported as its own category, excluded from *film* and *isolated puddles* - otherwise a legitimately wet water-table pool reads as a defect. This ends preprocessing; (2) `mesh_convergence_study.py` runs the grid-independence study; (3) `run_Bayes_cal.py` calibrates the built case with HydroBayesCal. An **optional 3D extension** runs after step 1b (and after step 2 fixes the horizontal mesh): `add3d.py` writes the three 3D steering files (hydrostatic flux-convergence check, non-hydrostatic steady, unsteady; see the "Optional 3D extension" section below), then `vertical_convergence_3d.py` runs the vertical-layer (`dz`) grid-independence study - see the "Optional 3D extension" section below. Step 3 compiles the FlowTracker velocity ground truth into the calibration-points CSV (the point velocity, measured at **0.6·h**, approximates the depth-averaged velocity, so it is compared to TELEMAC `SCALAR VELOCITY` = sqrt(U²+V²) built from the **horizontal** components only), ensures the `.cas` outputs `SCALAR VELOCITY` (graphic-printout `M`), emits `config_Telemac.py`, and stages and launches HydroBayesCal's `bal_telemac.py`. **HydroBayesCal is a pip dependency** (`pip install 'hydromate[calibration]'`, requiring `>=1.4.4`: 1.4.2 ships the drivers *with* the package, 1.4.4 makes the multi-flow driver honour the config's `extraction` block): the driver is copied out of the installed package by `hydroBayesCal.copy_driver` and run in hydromate's own environment, so there is no checkout directory to point at and no second conda env to name. It is an *optional extra* because its surrogate stack (bayesvalidrox, gpytorch, scikit-learn) is irrelevant to building or running a TELEMAC case, so `bayescal.require_hbc` imports it lazily and explains the install if missing. The driver is still a subprocess - it is a script with an `argparse` main() that must run with TELEMAC sourced, and sourcing mutates the environment - but under `sys.executable`. Pass `checkout=` to develop against an unreleased driver; `--prepare-only` writes the CSV+config without launching - everything into `calibration-validation/`. HydroBayesCal reads the CSV's first four columns by position (id, x, y, z) and `<QTY>_DATA`/`<QTY>_ERROR` by name; `_ERROR` is a site-specific error in physical units added in quadrature to its built-in 10% measurement + 10% surrogate error.

### HydroBayesCal calibration (step 3) - `hydromate/bayescal.py` + `hydromate/campaigns.py`

Step 3 is **thin scripts over the package**: `run_Bayes_cal.py` (single discharge) and `run_Bayes_cal_multiflow.py` (multi discharge) each just declare the case-specific choices and call `hydromate.run_single_flow_calibration` / `hydromate.run_multiflow_calibration`. Both scripts live in `cases/case-template/` and every case folder. All logic - CSV compilation, `.cas` derivation, HBC config emission, driver staging, launching, the smoke test, resume - lives in `hydromate/bayescal.py`; the multi-campaign FlowTracker-to-CSV compilers in `hydromate/campaigns.py` (`adapter` = summary workbook + DGPS layer joined by ID; `transect` = taped cross-section + point gpkg keyed by vertical number; `inline` = inline-coordinate verticals; each keeps the 0.6-depth vertical and floors the propagated velocity error). Tests: `tests/test_campaigns.py`.

- **Single-flow** (`run_single_flow_calibration`): compiles `ground_truth.sources` into the velocity CSV, ensures the `.cas` prints `SCALAR VELOCITY` (`M`), emits `config_Telemac.py` via `calibration.emit_hbc_config`, stages `bal_telemac.py` and launches. `--prepare-only` stops before launch.
- **Multi-flow** (`run_multiflow_calibration`, `launch_mode` = `prepare`|`smoke`|`run`|`resume`): calibrates **one shared roughness against several steady discharges jointly**. The case script lists `hydromate.FlowSpec(name, discharge, kind, values, positions, duration, vel_err_floor)`. Each flow gets its own steering file derived from the built base `steady2d.cas` (only Q, the outflow stage from the synthetic rating at that Q, `DURATION`, and the results name change) and its own calibration CSV; they are joined into one 57-point (e.g.) observation/output space by the **additive hydrobayescal extension** `hydroBayesCal.telemac.multiflow_telemac.MultiflowTelemacModel` + `bal_telemac_multiflow.py` (wraps one stock single-flow `TelemacModel` per flow; single-flow users untouched). `--smoke` runs an isolated 3-level tiny-run plumbing test (checks per-run JSON accumulation, that rows differ with ks, and the combined shape) in ~15 min before committing solver hours; `--resume` reuses each flow's completed initial design from `flow-<name>/.../restart_data/initial-model-outputs.json` (only_bal_mode) and skips straight to surrogate + BAL.

**Lessons baked in (all fixed / guarded):**
- **`prior_samples` is a memory trap.** gpytorch predicts the surrogate at every prior sample by building a `prior_samples x prior_samples` dense covariance **per calibration location**; 25000 OOM-kills a 16 GB box. `calibration.prior_samples` (config, default **5000**) is emitted into both single- and multi-flow configs; a low-dimensional roughness posterior needs only a few thousand. Raise only with RAM.
- **HydroBayesCal fixes (in the checkout, backward compatible for existing users):** (a) `control_telemac.rewrite_steering_file` matched only `KEYWORD = value`; hydromate `.cas` files use `KEYWORD : value`, so per-run RESULTS-FILE renames silently no-op'd - now matches `=` or `:`. (b) `function_pool.update_json_file` used `key in output_data` with **int** calibration-point IDs against JSON's **str** keys, so every run overwrote instead of appending (only run 1's outputs survived, rest read as zeros) - now `str()`-normalises keys. (c) `bal_functions.select_indexes` called `np.in1d`, **removed in NumPy 2** - now `np.isin`.
- **The staged driver extracts the `last` (converged) SELAFIN frame, not the `mean_last` window** (which would average a dry-start transient into the calibration values).
- **Data comparability governs which flows are calibratable - and verify the discharge label itself.** Compare per-campaign mean U, depth, and spatial span: a few-point survey confined to slow, shallow near-bank margins samples partially-wet cells the 2D depth-averaged model represents poorly, not the modelled channel (the Inn KB15 March-2026 campaign - 5 margin verticals, ~0.58 m / 0.02-0.52 m/s - was first excluded under a **mislabelled Q=168** that made the model look ~5x too fast; at the true **45.8 m3/s** the magnitudes match to order, but the margin points still carry the DEM too-shallow/too-fast bias and add no discharge diversity, so it stays excluded from velocity calibration). Use WATER DEPTH / flood-extent for high flow instead - **wadeable FlowTracker velocity surveys are safety-capped at low flow (~46-48 m3/s)** (river entry at high discharge endangers the operators), so velocity calibration cannot gain discharge diversity. Down-weight a single-cross-section campaign by raising its `vel_err_floor` (KB15 Nov-2025: 0.05 m/s) so its many low-variance points do not dominate the joint likelihood. `MultiflowTelemacModel` also fails fast on all-zero or all-identical initial-design rows per flow.

**Optional 3D extension (`add3d.py`, `hydromate/threed.py`).** The 3D path sits **strictly after the 2D path** and depends on it twice over: a 3D run is only built (1) once the 2D run has produced its **hotstart** result (`initial_run.py` → `r2d.slf`; the 3D case is seeded from it and would otherwise start from a dry bed), and (2) once the **2D mesh-convergence study** has settled the **horizontal** resolution - the 3D case reuses that same horizontal mesh, so building 3D before step 2 means resolving the vertical on an unvalidated horizontal grid. After `initial_run.py` has produced `r2d.slf`, `add3d.py` writes **exactly three** steering files for `telemac3d.py` next to the 2D case (no rebuild) via `threed.build_3d_cases` (which reads `r2d.slf` **once** and shares the inferred levels/turbulence/dt across all three; the per-case script is a thin wrapper printing `workflow.format_3d_cases`): (a) **`hotstart3d_hydrostatic.cas`** - `NON-HYDROSTATIC VERSION : NO` (no PPE keywords), constant in-file Q/H, `HYDROSTATIC_N_STEPS` (30k) fixed steps with `LISTING PRINTOUT PERIOD : 100` so the sortie carries enough `FLUX BOUNDARY` printouts to check when the boundary fluxes converge in a steady telemac3d run; results go to `r3d-hydrostatic.slf`/`r3d-2d-hydrostatic.slf`; (b) **`hotstart3d_hydrodyn.cas`** - the non-hydrostatic steady run with the same in-file prescribed Q (in) and H (out); (c) **`unsteady3d.cas`** - non-hydrostatic, hydrograph-driven via `unsteady.build_unsteady_3d_case(out_name=...)`: Q(t) inflow + outflow SL(t) from the **same** `inflow-hydrograph.liq` as `unsteady2d.cas` (skipped with a notice unless `boundaries.inflow` is a varying series). `--run [hydrostatic|hydrodyn|unsteady]` launches one of them streaming (default: hydrostatic). All three (and every `build_3d_cas` product) emit `PRINTING CUMULATED FLOWRATES : YES` - a valid TELEMAC-3D keyword - so `hydromate.sortie` can read the fluxes. Every case is **hotstarted from the 2D run**. The default hotstart is the **TELEMAC v9+ true 2D→3D continuation** (`FILE FOR 2D CONTINUATION` + `FILE FOR 2D CONTINUATION FORMAT : 'SERAFIN'` + `INITIAL TIME SET TO ZERO`), which lifts the 3D free surface + horizontal velocities from the final 2D state (in v9 this keyword alone triggers the continuation - the old `2D CONTINUATION` flag is gone). Because a thin/supercritical 2D inflow can make `telemac3d` abort with `DEBIMP_3D: PROBLEM ON BOUNDARY` on the prescribed-Q inflow, a cold-start `INITIAL CONDITIONS : 'CONSTANT DEPTH'` seed (median wetted 2D depth, which over-wets the inflow) is emitted **commented-out as a fallback** - and is the `build_3d_cas(hotstart="constant_depth")` mode the vertical convergence study uses so every per-layer run reaches steady state. `INITIAL GUESS FOR DEPTH : 1` and a `MINIMAL VALUE FOR DEPTH` floor (guards the sigma transform against dry columns) back both modes. TELEMAC-3D has **no Delft3D-style constant-dz z-layers**, only **sigma planes** (`NUMBER OF HORIZONTAL LEVELS` + `MESH TRANSFORMATION : 1`), so `infer_vertical_layers` sizes the level count from the 2D depth/cell size to target `dz ~ dx/2` while keeping `dz >= dx/4` (the "max 4× finer" rule). The turbulence model reuses the 2D `select_turbulence_model` quality check, mapped onto the 3D numbering (k-epsilon 3, Smagorinski 4, **Spalart-Allmaras 5** - 3D numbers S-A 5, not the 2D 6) with the vertical model paired per TELEMAC's rules (S-A must be 5 in both directions; k-epsilon→3; Smagorinski→vertical mixing length 2). TELEMAC-3D cannot run finite volumes (always FE), has no zonal `FRICTION DATA FILE` (a single representative `LAW OF BOTTOM FRICTION` + `FRICTION COEFFICIENT FOR THE BOTTOM` is written - **not** spatially equivalent to the 2D zonal friction), and has **no `DESIRED COURANT NUMBER`** keyword - so the fixed `TIME STEP` is sized for a target Courant of 0.6 from the 2D velocity and the cell sizes (the 2D steady run's `desired_courant` default is the safer 0.30, since its dry start is less stable than this hotstarted 3D run; raise either toward ~0.9 to march to steady state in fewer steps). It also has **no steady-state auto-stop** (the 2D `STOP IF A STEADY STATE IS REACHED` keyword does not exist in TELEMAC-3D), so the 3D run always marches the full `NUMBER OF TIME STEPS`. For wetting/drying robustness the 3D numerics use **MURD PSI advection with the locally-implicit option** for velocity *and* k-epsilon (`SCHEME FOR ADVECTION ... : 5` + `SCHEME OPTION ... : 4` - robust on tidal flats without the sub-iteration blow-up the default MURD option hits), **mass-lumping** on depth+velocity with `TREATMENT OF NEGATIVE DEPTHS : 2`, segment-wise `MATRIX STORAGE : 3`, and `ACCURACY FOR PPE : 1.E-4` (the v8.1+ default; tighter just wastes iterations on spin-up). The boundary conditions reuse the 2D `PRESCRIBED FLOWRATES`/`ELEVATIONS`/`VELOCITY PROFILES` plus a logarithmic `VELOCITY VERTICAL PROFILES`. `add3d.py --run` launches `telemac3d.py` via `run_solver_streaming(..., solver="telemac3d", duration=dt*n_steps)` (live listing + progress bar; 3D has no DURATION keyword, so the bar spans the fixed step count).

**3D vertical-layer convergence (`vertical_convergence_3d.py`, `hydromate/vertical_convergence.py`).** Choosing the number of vertical layers is a **separate discretization decision that the 2D mesh-convergence study never addresses** (step 2 only varies the horizontal cell size), so the vertical resolution `dz` needs **its own grid-independence study** - run after `add3d.py`. It is the 3D analogue of the 2D study: where the 2D study varies the horizontal cell size, this varies the **number of sigma layers** (`NUMBER OF HORIZONTAL LEVELS`) on the *same* (already 2D-converged) horizontal mesh. `run_vertical_convergence` runs the hotstarted 3D case once per layer count (a ladder around the inferred baseline, or explicit `counts=`), each in its own `postprocessing/vertical-convergence/L<n>/` folder with the geometry/`.cli` symlinked in (no mesh rebuild) and `build_3d_cas(..., n_levels=<n>)` forcing the level count (the time step adapts to the resulting `dz`), samples depth-averaged water depth + scalar velocity at the probe points from the run's `2D RESULT FILE`, and reports the relative change / observed order / GCI keyed on the layer thickness `dz` (reusing `convergence`'s report maths; the report `recommendation()` picks the **fewest grid-independent layers**). The TELEMAC run is injectable (`simulate=`) for unit tests. The whole vertical study was verified end-to-end against the real `telemac3d` solver on `ering-revised`.

**Gain-lose reaches (`gain_lose` config block, `hydromate/gainlose.py` + `watertable.py` + `fortran.py`).** A reach that loses flow into a porous body (a gravel bar, an alluvial patch) and regains it downstream. A 2D depth-averaged model has no subsurface, so the underflow is represented as an internal **withdrawal** where water infiltrates plus an **injection** where it resurfaces, generated into a `USER_RAIN` routine (`FORTRAN FILE` + `RAIN OR EVAPORATION : YES` + rate 0; TELEMAC compiles it per run). The routine is **depth-limited** - the withdrawal tapers to zero as a cell approaches `min_depth` and is additionally capped at half the water available above that floor per step, so a sink can *never* dry a cell (TELEMAC's own source terms have no such guard, which is what collapsed the CFL-adaptive time step in the isar-2025 T2/T3 rungs) - and **mass-exact**: whatever is withdrawn is reinjected in the same step, so no net sink appears in the boundary budget (a permanent sink S would make the steady budget read `|Q_in| - |Q_out| = S` and put a floor under the relative flux imbalance, so no `hotstart2d.cas` would ever be written). **Two independent choices:**
- **Where** (`faces`): **`water-table` (default)** derives both faces from the body's phreatic surface and needs *nothing drawn* - a node **loses** where it is wet and its free surface stands above the table, and **gains** where the table stands above the bed, evaluated inside the zone polygon buffered by `zone_buffer` (default one channel cell, so the losing face can reach the wetted channel beside a bar). The classification happens **at run time**, so the faces move with the stage rather than being frozen at build time. This is the default because it is genuinely fuzzy where percolation begins and ends. `faces: lines` instead pins the exchange to the `int-*` lines of `boundaries.liquid_boundaries`, each buffered to a strip - for a surveyed seepage face, or to reproduce a calibrated exchange (isar-2025 uses it).
- **How big** (`conductivity` or `discharge`): `conductivity` (kf) drives it by default via Green-Ampt's saturated limit `f = kf (h + Lz + hf) / Lz` at the local head, so the exchange **responds to water level** and kf is the calibration parameter; `discharge` overrides it with a measured total normalised over the losing face. Both work with either `faces` setting. **kf is exposed to HydroBayesCal as `f.HMP_KF`** (`targets.PARAMETER_CATALOG` → "POROUS ZONE kf (gain-lose)"): it is emitted as a run-time *assignment* rather than a `PARAMETER` declaration precisely so HBC's `f.` mechanism - which rewrites the line whose text left of `=`/`:` matches - can find it, and `calibration.emit_hbc_config` passes `fortran_file: user_rain.f`. Riverbed kf spans orders of magnitude (clean gravel 1e-2..1e-1, moderately colmated 1e-4..1e-3, silted 1e-7..1e-5), so calibrate rather than assume - values from Calver (2001), *Riverbed Permeabilities: Information from Pooled Data*, Ground Water 39(4):546-553, doi:10.1111/j.1745-6584.2001.tb02343.x.

**The water table** (`water_table: phreatic`, `hydromate/watertable.py`) is the surface joining the two channel levels the body exchanges with - that *is* the water table of the through-flow, and its gradient is what drives the exchange. It is fitted as a **plane** (five numbers, so the Fortran needs no per-node array) from the `int-*` lines (`faces: lines`) or, with `faces: water-table`, from the **channel water surface at each end of the zone's centerline extent** - which is what makes drawn lines optional. `water_table_levels` pins them explicitly. Besides locating the faces it does two things: the **pre-wet seeds any ground below it**, so closed depressions *on* the bar start full (they can never fill otherwise - no surface flow reaches a hollow sitting above the channel, and `drainable_prewet` deliberately refuses to seed behind a rim), and the **patch drain** (`patch_drain`) tapers to zero *at the table* instead of at `min_depth`, so it clears standing water off the bar top but cannot empty a pool that cuts below the saturated zone. `water_table_depth` is the single place the clip-to-the-zone rule lives - extended across a reach the plane would stand above every bed lower than the bar (22 598 m² of it on isar-2025). `gainlose.derive_faces` / `estimate_exchange` report the faces and the discharge they imply **at build time**, before any solver run. On isar-2025 the polygon-derived route gives a 5.30 ‰ table and 391 m² losing / 208 m² gaining → 0.213 m³/s at kf=3e-4, against the 0.065 m³/s the drawn lines prescribe - i.e. in polygon mode kf must be calibrated, which is exactly why it is exposed. The block was called `percolation:` while the feature lived in the isar-2025 case; that spelling still loads (mapped `mode`→`enabled`, `losing_region`→`faces`) with a deprecation warning, and `cfg.percolation` remains an alias for `cfg.gain_lose`.

**Optional unsteady extension (`unsteady_run.py`, `hydromate/unsteady.py`).** Turns the converged steady case into a **hydrograph-driven quasi-steady** run (a flood wave discretised as a sequence of steady discharges), **hotstarted from the steady result** `r2d.slf` (`PREVIOUS COMPUTATION FILE`, clock reset to zero) - so it runs strictly after step 1b. The flood wave `Q(t)` comes from **this case's** `boundaries.inflow` **time series** (a genuinely varying series; a constant Q is the steady case). Unlike the manual tutorial, hydromate **does not re-define the boundaries**: the generated `boundaries.cli` is reused unchanged (inflow `4 5 5`, outflow `5 4 4`), the inflow discharge is driven by the `LIQUID BOUNDARIES FILE` (Q(t) per inflow; SL(t) per prescribed-elevation outflow at the rating stage, else the fixed `prescribed_elevation`) and the downstream level by its prescribed elevation - **no** `5 5 5`→`4 5 5` find-replace, no separate `boundaries-unsteady.cli`, no `STAGE-DISCHARGE CURVES` keyword (that is the alternative route). The build serializes the FRONT2 liquid-boundary numbering to `liquid-boundaries.json` (via `boundary.dump_liquid_boundaries` in `pipeline.run`), so `unsteady.py` recovers the boundary order **without re-meshing**. `build_unsteady_case` writes `unsteady2d.cas` with quasi-steady numerics (`NUMBER OF CORRECTIONS OF DISTRIBUTIVE SCHEMES : 2`), a distinct `RESULTS FILE` (`r2d-unsteady.slf`, so it does not clobber its own hotstart input), and optional `CONTROL SECTIONS` (`write_control_sections` parses the `.cli`, grouping consecutive same-tag rows **by rank** into one section per open-boundary segment, endpoints = that run's first/last global node - so the run reports the flux across each boundary). `unsteady_run.py` has **in-script toggles**: `MODE_3D` (`build_unsteady_3d_case` drives the same hydrograph on the non-hydrostatic 3D mesh via `threed.build_3d_cas(unsteady=True, liquid_boundaries_file=..., duration=...)`, spanning the hydrograph by step count since 3D has no `DURATION`), and `GAIA_ENABLED` / `GAIA_BEDLOAD` / `GAIA_SUSPENDED` (fold into `morphodynamics`, adding `COUPLING WITH : 'GAIA'` + `GAIA STEERING FILE` + `COUPLING PERIOD FOR GAIA` to whichever run is built here - so **GAIA is coupled to both `unsteady2d.cas` and `unsteady3d.cas`** (and the steady case), sharing one generated GAIA `.cas`). Suspended sediment is carried as TELEMAC tracers by GAIA, needing no manual `NUMBER OF TRACERS`. `steering.write_gaia_cas` emits a **damocles-valid** GAIA steering file (verified against `gaia.dico`): it references the **same `GEOMETRY FILE` + `BOUNDARY CONDITIONS FILE`** as the coupled run (GAIA needs both even when coupled) and its results keyword is `RESULTS FILE` (**not** `GAIA RESULTS FILE`, which is not a GAIA keyword - fixed), plus `BED LOAD FOR ALL SANDS` / `SUSPENSION FOR ALL SANDS` and the bed-process capacities driven by the `morphodynamics` config block: `MORPHOLOGICAL FACTOR` (`morphological_factor`, bed-evolution acceleration over a hydrograph), `SLOPE EFFECT` + `FORMULA FOR SLOPE EFFECT` + `FRICTION ANGLE OF THE SEDIMENT` (`slope_effect`/`slope_formula`/`friction_angle`), `SECONDARY CURRENTS` + `SECONDARY CURRENTS ALPHA COEFFICIENT` (`secondary_currents`, spiral-flow bedload deviation in bends), `NUMBER OF LAYERS FOR INITIAL STRATIFICATION` + `ACTIVE LAYER THICKNESS` (`bed_layers`/`active_layer_thickness`), `PRESCRIBED SOLID DISCHARGES` (`prescribed_solid_discharges`, sediment supply per liquid boundary in FRONT2 order), `CLASSES TYPE OF SEDIMENT` (`sediment_type`), `MASS-BALANCE` and the GAIA `VARIABLES FOR GRAPHIC PRINTOUTS`. Pass `--run` to also launch the solver. The steering writers (`steering.write_cas`, `write_gaia_cas`, `threed.build_3d_cas`) are unit-tested without the solver (`tests/test_unsteady.py`).

**Optional OpenFOAM free-surface extension (`openfoam_preprocessing.py` / `openfoam_run.py`, `hydromate/openfoam/`).** A **3D two-phase (VOF) `interFoam` case** built from the same config, the same geodata and the same converged `r2d.slf` as the TELEMAC case, into `<sim_dir>/openfoam/`. Entirely **additive**: a config with no `openfoam:` block gets the default `OpenFoam` dataclass and nothing in the TELEMAC path consults it. It exists because `simpleFoam` cannot represent a water surface with a gradient (so the air-water interface must be modelled) while the air phase itself is of no interest and is what usually wrecks these runs.

**Meshing - extrude, don't snap (`openfoam/polymesh.py` + `openfoam/mesh.py`).** hydromate writes `constant/polyMesh` itself (as `selafin.py` writes SERAFIN), because a river bed is a **single-valued height field** z_b(x,y) and can therefore be *followed* rather than snapped to. snappyHexMesh's castellate-and-snap buys nothing on such a surface and costs the sliver/negative-volume repairs that make it painful. The mesh is a **structured (i,j,k) lattice warped onto the bed**: in plan a uniform Cartesian grid of spacing `cell_size`, optionally **rotated onto the reach's principal axis** (`align_to_flow`, PCA of `geodata.channel_centerline`; isar +32.9 deg), with columns outside the footprint absent, hole-filled and reduced to the largest 4-connected block; in the vertical `n_layers` sigma layers per column. Result: **all-hexahedral, conformal by construction** (levels are computed at the *plan vertices*, so neighbouring columns of different height share their corner points exactly - no merging, no hanging nodes) and **bed-fitted** (the bottom face of the lowest cell *is* the DEM, not a staircase). `polymesh.assemble` enforces the format contract - internal faces first in **upper-triangular** order, `owner < neighbour`, every face oriented owner→neighbour using the known cell centres - and `polymesh.validate` additionally checks **cell closure** (face area vectors summing to zero) before anything is written. Files are ASCII (written once, read once); the run's own output is `writeFormat binary`. Verified: `checkMesh` reports **Mesh OK, 1,579,074 hexahedra, one region, upper triangular ordering OK** on the isar case at 0.5 m / 14 layers.

**The lid is the fix for the air phase.** The lid is clamped `freeboard` (0.5 m) above the **2D free surface** instead of being a flat plane over the terrain, so most air cells simply never exist (isar: only 9.7% of cells start as water, and a flat lid would be far worse), the `atmosphere` patch stays close to the interface where `inletOutlet`/`totalPressure` behave, and the surface still has room to move. It is grey-**dilated** (`lid_dilation`, default **2** - 1 left a single 70.16 deg severely non-orthogonal face where the lid dipped over a shallow cell) then smoothed (`lid_smoothing`), so it is never *below* the surface it came from and has no dents that pinch the air into slivers. `domain: wetted` further trims the plan footprint to the 2D wetted extent buffered by `wet_margin` (isar: 28,198 m2 of the 66,000 m2 ROI).

**The other two air levers** are in `openfoam/dicts.py`: **`MULESCorr yes`** (semi-implicit MULES) removes the alpha equation's own Courant limit, so `maxCo`/`maxAlphaCo` run at ~0.9 instead of the tutorials' 0.2; and **`system/fvConstraints`** carries a **`limitVelocity`** constraint at `air_velocity_cap` (default 5x the reach's p95 water speed, isar 4.5 m/s). Water never reaches the cap; a runaway air jet does, and that is what collapses the time step. Also `momentumPredictor no` (buoyancy dominates) and `nNonOrthogonalCorrectors 2` (a bed-following mesh *is* non-orthogonal where the bed is steep).

**Two-stage run.** `system/stage1-spinup/` and `system/stage2-run/`; `dicts.activate` copies one into `system/`. The first moments after a hotstart are the least like the converged flow - the 2D state is depth-averaged, so at t=0 there is no vertical structure at all - so **stage 1** runs briefly (`spinup_time`) at `spinup_courant` 0.3 with **half** the interface compression (`Gauss interfaceCompression vanLeer 0.5`; in OF9 cAlpha lives in the *scheme*, so dropping compression entirely instead demands a legacy `cAlpha` fvSolution key and smears the surface through the whole spin-up) and upwinded momentum; **stage 2** restarts (`startFrom latestTime`) at `max_courant` 0.9 with full compression and `limitedLinearV 1`. `fvSchemes` also needs `wallDist { method meshWave; }` for kOmegaSST.

**Boundary conditions (OF9-verified against that install's source + the `waterChannel`/`weirOverflow` tutorials).** Inlet/outlet patches come from the **same `boundaries.liquid_boundaries` layer that drives the `.cli`** (`boundary.liquid_line_details`), one patch per line, so 2D and 3D take flow in and out at identical places and each line's `Target flow` gives its own Q (isar: `inlet-1` 1.6, `inlet-2` 0.8 m3/s). Inlet: `variableHeightFlowRateInletVelocity` + `variableHeightFlowRate` alpha - the inlet **stage is an outcome, not an input** (prescribing Q *and* a depth over-determines it). Outlet: the case's own `outflow_condition` becomes `prghPressure` with a hydrostatic `p` profile below the target level plus an `inletOutlet` alpha profile 1 below / 0 above - the direct analogue of TELEMAC's `PRESCRIBED ELEVATIONS` (isar: 815.347 m from the section rating at Q=2.4); `free` still selects the weirOverflow-style outfall. Bed/banks: `noSlip` + **`nutkRoughWallFunction` with per-face `Ks`** from the same `geodata.roughness_zones` that drives `FRIC_ID`/`.tbl`.

**Initial fields (`openfoam/fields.py`, `openfoam/hotstart.py`).** `alpha.water` is the **submerged fraction of each cell** below the 2D free surface (a one-cell-sharp interface, far better than `setFields` boxes); `U` is the 2D depth-averaged velocity in water, scaled by alpha, zero in air, deliberately **uniform over the depth** (the vertical structure is what the 3D run is *for*); `p_rgh` uniform 0; k/omega uniform from the reach's own depth and velocity. `State2D` samples the 2D result **nearest-node on a KD-tree, not P1 on the element table**: a SELAFIN merged from a parallel run is not a clean triangulation (isar: 4,393 coincident nodes and 66,759 zero-area triangles of 460,314, which makes matplotlib's `TrapezoidMapTriFinder` reject the mesh outright), and nearest-node costs nothing in accuracy because the 2D mesh is *finer* than the 3D lattice it seeds - `resolution_check` warns if that ever reverses.

**The honest limitation (`openfoam/quality.py`).** `nutkRoughWallFunction` needs the first cell **centre** above the roughness crests (`y1 > ks`, i.e. a bed layer ~`2 ks`), so `auto_bed_layer` pins the bed layer to **2x the wetted-median ks** (isar 0.10 m; the *wetted* median, because the dry floodplain's vegetation ks 0.5 m has no bearing on a wall function under water). Even so, on isar **41% of wetted bed faces** still have `y1 < ks` - the reach's roughness (ks 0.085-0.5 m) is a large fraction of its depth (median 0.22 m). OpenFOAM does **not** fail there: it clamps y+ to `e/E` and carries on, so the run completes and the near-bed velocity is simply not physical. Refining towards the bed makes it worse, not better. The report states the share per build; read such a result as bulk flow, not as a resolved bed boundary layer. `quality.py` also reproduces `checkMesh`'s **own** definitions exactly - `face_geometry` (triangle-fan centroids: a terrain-following quad is non-planar, so its centre is not the corner average), `cell_geometry` (pyramid decomposition), skewness normalised by the **face half-width** floored at `0.2|d|` (not by `|d|`, which understates it ~7x), aspect ratio as `max(component ratio, hydraulic ratio)` (the component form dominates on flat cells: 16.7 where the hydraulic form alone reads 3.1), and the mean non-orthogonality as `acos(mean(cos))`. Verified against `checkMesh` on the isar mesh to 3 significant figures (60.11 deg / 7.84 deg, skew 4.025, aspect 16.66, identical volumes). `MeshReport.usable` (structurally sound: no zero/negative volumes) is deliberately **weaker than `.ok`** (passes every checkMesh check): a mesh cut from a real DEM routinely carries a few marginal faces at survey steps and seams - isar has exactly one skew face in 4.9 million, which no lid smoothing moves because it comes from the bathymetry - and refusing to run on that would be refusing to model the terrain. `runtime.check_mesh` blocks only on its `_FATAL_CHECKS`.

**Running and reporting.** `OpenFoamRuntime` extends the new shared `env.ShellRuntime` (extracted from `TelemacRuntime`, behaviour unchanged) and sources `openfoam.bashrc` per command: `checkMesh`, `decomposePar` (**scotch**, since the wetted corridor is sinuous and a geometric split would hand some ranks empty space), `mpirun -np N interFoam -parallel`, `reconstructPar`. Output is **streamed** with an `OpenFoamProgress` bar sharing the new `progress.ProgressBar` with the TELEMAC renderer; it shows **`Co` and `dt`**, which are the diagnostic - a healthy run holds `dt` near the Courant target, a misbehaving air phase shows `dt` falling by orders of magnitude while the clock barely advances. `openfoam/report.py` reads the `surfaceFieldValue` monitors written into `controlDict` (`sum(phi)` **weighted by `alpha.water`**, so it is the water discharge, not water+air) into `discharge-convergence.csv`/`.png` and judges the relative inlet/outlet imbalance against the **same `hydrodynamics.flux_tolerance`** the 2D run is judged by, so 2D and 3D are held to one standard. CLI: `hydromate openfoam <config> [--check] [--cell-size <m>] [--layers <n>]` (`--check` reports the cell count without building). Tests: `tests/test_openfoam.py` (no OpenFOAM, no solver).

The mesh-convergence study (`hydromate/convergence.py`, step 2; `cases/example-Inn/mesh_convergence_study.py`, which creates and works in its own `hydromate-case/mesh-convergence/` folder) runs the same steady sim on a **four-mesh r=1.3 ladder** (`ratio_levels`: one coarser x1.3, the configured baseline, two finer /1.3 and /1.3² - Celik et al. 2008 recommend a grid refinement factor **r >= 1.3**; closer-spaced grids like the old ±20% `percent_levels`, kept only for backward compat, drown the grid-to-grid differences in solver noise and degenerate the GCI denominator r^p−1) at constant discharge with TELEMAC's variable time step (per-mesh CFL dt), samples water depth + scalar velocity at the ground-truth probe points (`default_probes`), and judges convergence on the **GCI of the finest grid triplet** (observed p clamped to `THEORETICAL_ORDER` 2 for the GCI; an **asymptotic-range check** `GCI(med)/(r^p·GCI(fine)) ∈ 0.8..1.25` decides whether the GCI is trustworthy, else the finest successive relative change is the fallback - `ConvergenceReport.verdict_basis`) vs a tolerance (default **5%**, `DEFAULT_TOLERANCE`; Celik: 5-10% is engineering accuracy). Each level is built with **`mesh.size_scale`** (= level channel size / config `channel_size`), a global multiplier applied to *every* target edge length **including the per-zone `Max Edge Length (m)` gpkg values** - scaling only `channel_size`/`floodplain_size` does nothing when the gpkg carries that field (the bug that invalidated the first ering study: five "levels", one mesh). The study is **resumable** (each level folder gets a `level.json`; on re-run a prompt offers reusing completed levels, QoI re-extracted from their `r2d.slf`; size-mismatched levels re-run) and **extensible**: when not converged it offers up to `MAX_EXTRA_LEVELS` further /1.3 refinements one at a time, each prompt showing a **runtime estimate** (log-log fit of measured runtimes, theoretical t~dx⁻³ fallback) and the **mesh-validity check** of the candidate size; non-interactive sessions auto-resume and auto-stop (no hang). A refinement that **fails to mesh/run** (e.g. BAMG gives up even after its retries, or the solver diverges) is caught as the practical refinement limit: the extension stops and the report is written from the levels already completed, instead of crashing the study. **Auto-refinement mode** (`run_mesh_convergence(auto_extend=True)`, exposed by the per-case `mesh_convergence_study.py` as `python .../mesh_convergence_study.py mode='auto-refinement'`) auto-approves the resume prompt and every extension (no prompts, interactive or batch) so the study marches finer one grid at a time until it converges, exhausts `AUTO_MAX_EXTRA_LEVELS` (default 8, vs. the interactive `MAX_EXTRA_LEVELS` 3), or a level fails. Every level's report row carries the `hydromate/mesh_validity.py` checks: shear velocity from the fully-rough log law, wall **y+** (O(10⁴) in rivers, always passes - reported as standard), roughness Reynolds **ks+** (>=70 fully rough for the Nikuradse law), **dx vs ks** (dx < channel ks = roughness double-counting risk; fires first under refinement), and **turbulence-model consistency** (`steering.turbulence_pick_for_dx` vs the pinned baseline model). Every per-level build is **pre-wetted** (`INITIAL_DEPTH`, default 0.5 m -> `initialization.prewet_depth`): the channel mesh-zone nodes are hotstarted with that water depth so the solver need not advance the wetting front from a dry bed (see "Pre-wetting" below). `ConvergenceReport.to_xlsx()` writes a **styled .xlsx** (openpyxl) to `mesh-convergence/` (incl. the validity rows) and `recommendation()` picks the **coarsest grid-independent cell size** (convergence vs. compute-time tradeoff, with the runtime speed-up vs. the finest; under a GCI verdict with no rel-change-adequate level it recommends the medium grid of the converged triplet). The TELEMAC run is injectable (`simulate=`) so the report maths/xlsx are unit-tested without the solver (`tests/test_convergence.py`, `tests/test_mesh_validity.py`). Results SELAFINs are read with the minimal `selafin.read_slf` (the writer's counterpart; single/double precision, multi-frame, returns the last frame); `_geom_stats` drops the zero-length edges that merged parallel results carry at subdomain interfaces (else min-edge/dt report as 0/NaN).

A build needs a **ROI boundary polygon** (`geodata.boundary`, a closed polygon/polyline in EPSG:25832; the Inn example uses `cases/example-Inn/user-sources/geodata/roi-kb15.gpkg`) and `boundaries.liquid_boundaries` (both set in the Inn config). The steady **inflow Q comes from this case's `boundaries.prescribed_flowrate`** (m³/s) - the shared `hydromate.prepare_steady_inputs` helper (used by `preprocessing.py` and the mesh-convergence script) reads it from the config rather than a value hard-coded in any script, so each case uses its own discharge. A constant-Q `boundaries.inflow` series is then **auto-synthesised** at that discharge when missing (`boundaries.inflow` itself is optional - only a *varying* series triggers the unsteady case), and the outflow rating `boundaries.stage_discharge` is synthesised from a normal-flow curve when the `stage_discharge` outflow condition is active and none is given (the default `outflow_condition: elevation` needs no rating, just `boundaries.prescribed_elevation`), so the only machine-specific thing to set for a build is `telemac.pysource`.

## Structures: dams, weirs, walls and buildings (`hydromate/core/structures.py`)

**No STL anywhere, and that is not a limitation.** STL is a `snappyHexMesh` requirement: that mesher snaps a background block onto a triangulated surface, so every solid must arrive as triangles. hydromate writes `constant/polyMesh` directly (and `geometry.slf` for TELEMAC), so a structure only has to declare **where its footprint is** and **how high it stands** - both ordinary vector attributes. A structure layer is therefore a plain GeoPackage QGIS authors natively, with no CAD step and no format QGIS cannot round-trip.

**Geometry**: a **polygon** is the footprint directly; a **line** is buffered by its `Width (m)` (flat caps, mitred joins - a lozenge with rounded caps would over-block the channel at each end), which is how one actually draws a wall or a dam crest. **Height**: `Crest (m)` gives a *level* crest (dam, weir, floodwall); `Height (m)` gives a crest that *follows the terrain* (embankment, levee of constant build height). Neither is a sane default for the other, so the field the user fills in is what decides.

**Two modes, and the choice is hydraulic.** `overflow` (dam, weir, embankment, levee, block ramp) **raises the bed to the crest**: the structure is terrain the DEM did not carry, the plan mesh is unchanged, and water passes over it - identical in both solvers. `solid` (wall, floodwall, building, pier) **removes the footprint from the domain** so its sides become no-slip walls from bed to lid; use it for anything never overtopped, since it is both cheaper (no cells inside the obstacle) and more correct (a real vertical face rather than a very steep bed with a sliver of cells on top). The mode comes from the `Type` text by substring - the same convention as `classify_zone` - or from an explicit per-feature `Mode` column. Unrecognised text is `overflow`, deliberately: raising the bed keeps the domain connected and lets water pass, whereas wrongly blanking a footprint would silently wall off part of the reach. Note `block` is **not** a solid keyword - a *block ramp* is overtopped by design while a *concrete block* is not, so the word carries no usable signal.

**Where the two solvers necessarily differ**, and it is reported rather than left implicit: a 2D depth-averaged mesh has no vertical wall to remove, so `solid` structures are burnt into the TELEMAC bed as crest + `structures.solid_freeboard_2d` (default 2 m) - the standard way a floodwall is represented in TELEMAC - while OpenFOAM gets the genuine vertical face. In the OpenFOAM mesher the blanking is applied **after** `binary_fill_holes` in `build_plan_grid`: a building punched out of the domain *is* the interior void that hole-filling exists to close, so blanking first would simply be undone. If blanking disconnects the domain the build **warns** ("a solid structure has cut the domain in two") instead of silently deleting the far side. Verified end to end on isar-2025 with a dam polygon plus a floodwall line: 225 mesh vertices raised to the crest, the wall's columns removed, and `checkMesh` reporting **Mesh OK, 61,002 hexahedra, Number of regions: 1** with the wall's faces folded into the `banks` patch.

Config: `geodata.structures` (the layer) plus a `structures:` block for the attribute names (`type_field`, `mode_field`, `crest_field`, `height_field`, `width_field`, `name_field`, `default_width`, `solid_freeboard_2d`). Applied by `core.structures.apply_to_bed` / `solid_footprint`, called from `mesh.build_mesh` (TELEMAC, via `_burn_structures`) and `openfoam.mesh.build_mesh`. Tests: `tests/test_structures.py`.

## Package structure: solver-agnostic core + pluggable backends

hydromate is being restructured so TELEMAC and OpenFOAM are **two backends behind one
case description**, rather than one tool with a second bolted on. The target layering is
`hydromate/core/` (solver-agnostic: config, geodata, boundaries, ground truth,
convergence maths, capabilities, registry) and `hydromate/solvers/<name>/` (one
subpackage per simulation code). **Nothing in `core` imports a solver.** The move is
staged; until a module has moved it stays at its historic `hydromate.<module>` path and
old imports keep working through shims.

**Capabilities and the `MODEL=` marker files (`hydromate/core/capabilities.py`).** Every
case carries one marker per solver at its top level - `MODEL=TELEMAC_ENABLED`,
`MODEL=OPENFOAM_DISABLED` - whose **name** says whether *the case* declares that solver
(`cfg.declared_blocks`, so the filename means the same on any machine) and whose **body**
is a strictly parseable status table: `#` comments, `key = value` header, then fixed-width
rows after `[capabilities]`. Each capability is reported on **three axes**, kept apart
because they have three different fixes: `implemented` (does hydromate support it *for
this solver* - `yes` / `no` = not yet / `n/a` = category error, e.g. OpenFOAM has no
depth-averaged mode while its morphodynamics is merely unbuilt), `configured` (does this
case ask for it, from the config alone), and `built`/`run` (do the artifacts exist - pure
path checks, never a parse, so a status report is fast and cannot fail). Unanswerable
cells render `-`, never a confident `no`. The files are **generated and gitignored**
(`cases/*/MODEL=*`, with `cases/case-template/MODEL=*` committed as the documented
example): they report the *currently available* setup, which is local state like
`hydromate-case/`. Refreshed by `pipeline.run`, by `openfoam.build_case` and by
`hydromate status <config> [--check-env] [--full]`; `refresh_markers` never raises, since
a succeeded build must not report failure because a status file could not be written.

**The solver registry (`hydromate/core/registry.py`).** A backend is described by a
`BackendSpec` - name, title, config key, the capability support matrix, and the
`built`/`run` path predicates - which is **metadata only**, deliberately separate from the
`SolverBackend` implementation that builds and runs. The spec modules
(`hydromate/solvers/{telemac,openfoam}/spec.py`) are import-light by contract: they use
the standard library plus attribute access on a `Config`, and nothing else. That is what
lets `hydromate status` - and, later, a QGIS plugin running inside the QGIS Python process
- answer "what can this case do?" without importing gmsh, rasterio, pandas or a solver.
Backends are discovered through the `hydromate.solvers` entry-point group, with a
hard-coded built-in list as a fallback for source checkouts that predate the group, so
"add your own" and "use ours" are the same mechanism.

**`hydromate/__init__.py` resolves attributes lazily (PEP 562).** `import hydromate` went
from 505 ms / 652 modules to **21 ms / 64 modules**, and a capability listing imports
**zero** heavy modules - measured, and asserted in `tests/test_capabilities.py` from a
subprocess so the rest of the suite's imports cannot mask a regression. The public API is
unchanged (`from hydromate import build_mesh` still works); `__all__` is written out
literally because linters and IDEs read it statically, and a test keeps it in step with
the `_EXPORTS` map.

Note: GDAL is **not** in `wrr-proj` by default in all cases - if `from osgeo import gdal` fails, prefer the TELEMAC pysource environment (which ships GDAL) or `rasterio`.

## Coordinate system - non-negotiable

**Everything is EPSG:25832 (ETRS89 / UTM Zone 32N), units in metres.** This was verified for the DEMs, all shapefiles, and the gauge metadata. Any new raster, mesh, or shapefile must use the same CRS, or downstream alignment (DEM interpolation onto the mesh, breakline snapping) will silently break.

Vertical datum varies across the gauge data (DHHN12 / DHHN2016 / "m NN" vs "m NHN") - check and reconcile datum before using gauge zero-point heights as model boundary elevations.

## Data layout and meaning

The Inn co-development dataset lives under `cases/example-Inn/user-sources/geodata/` (gitignored). The exact files evolve; what `cases/example-Inn/case-config.yml` currently points at:
- `dem-2020.tif` - baseline terrain (0.5 m DEM), `geodata.dem_initial`.
- `DEM-2025-20cm.tif` - 0.20 m high-res survey, `geodata.dem_target` (enables the morphodynamic/DoD path).
- `roi-kb15.gpkg` - the ROI / max-wetted-extent polygon (`geodata.boundary`), subreach KB15.
- `liquid-boundaries.gpkg` - inflow/outflow boundary segments (drives the `.cli`).
- `mesh-zones.gpkg` - polygons with a `Zone Name` (`channel`/`floodplain`) driving the anisotropic mesh (`geodata.mesh_zones`). `channel-centerline.gpkg` - the line channel cells are elongated along (`geodata.channel_centerline`).
- `roughness-zones.gpkg` - polygons with an integer **`Zone ID`** (1 = channel, 2 = floodplain) driving the friction zonation (`geodata.roughness_zones`); `roughness-table.csv` (`zone_id,ks`, e.g. `1,0.2` / `2,0.5`) maps each id to a Nikuradse ks (`geodata.roughness_table`). `interpolate_roughness` writes these as the per-node `FRIC_ID` + `BOTTOM FRICTION` and `steering` makes the matching `.tbl` (`<id> NIKU <ks> NULL`).
- `rating-curve.csv` - outflow `Q,WSE` stage-discharge curve (`boundaries.stage_discharge`); auto-synthesised from the geodata by `preprocessing.py` if absent.
- `iws-uas/`, `flowtracker2/`, `sediment/`, `muehldorf-gauge-XS/` - ortho/UAS imagery, FlowTracker velocity ground truth, GSDs, and gauge cross-section. `cases/example-Inn/user-sources/ground-truth/` holds the calibration ground-truth spreadsheets.

`-roi-clip.tif` files are generated clip outputs (from `preprocessing.py` / `hydromate clip`), not raw inputs.

### Material / region classification (MATID scheme)

Region/zone polygons assign a max triangle area (mesh density) and a `MATID` (material zone) used later for roughness and sediment classes in GAIA. Base resolution is ~0.2 m.

| MATID | name           | max area (m²) | type        | meaning                              |
|-------|----------------|---------------|-------------|--------------------------------------|
| 1     | riverbed_fine  | 1.0           | riverbed    | fine bed (sand, silt)                |
| 2     | riverbed_coarse| 4.0           | riverbed    | coarse bed (gravel, cobbles)         |
| 3     | block_ramp     | 0.5           | block_ramp  | block ramp / high-roughness structure|
| 4     | gravel_bank    | 2.0           | gravel_bank | gravel bank / transition zone        |
| 5     | floodplain     | 25.0          | floodplain  | floodplain, vegetated overbank       |

### Boundary-condition gauge data (Bavarian LfU)

The upstream (discharge) and downstream (water level) boundaries are driven by gauge exports from the Bavarian LfU (gkd.bayern.de) - discharge [m³/s] at Kraiburg (Q ≈ 47 m³/s for the Nov-2020 reference period), stage [cm] at Wasserburg (upstream) and Mühldorf (downstream). When such CSVs are supplied via `boundaries.inflow` / `boundaries.stage_discharge`, mind the **German LfU CSV format**:
- UTF-8 **BOM** on the first line.
- **Semicolon** delimiter, **comma** decimal separator (e.g. `43,3`).
- 9 metadata lines (Quelle, station name/no., Gewässer, gauge coordinates as `Ostwert`/`Nordwert`, `Pegelnullpunktshöhe`), a blank line, then a header row (`Datum;"...[unit]";Prüfstatus`), then `"YYYY-MM-DD HH:MM";value;Geprueft` rows.
- Times are MEZ (CET). Stage is in **cm**; convert to m and add the gauge zero-point height for absolute water-surface elevation.

Read with `pandas`: `pd.read_csv(path, sep=';', decimal=',', skiprows=10, encoding='utf-8-sig')`.

### Ground-truth & calibration data (`cases/example-Inn/user-sources/ground-truth/`)

Field measurements that become **calibration targets** for HydroBayesCal, ingested by `ground_truth.py`. The canonical input is the tidy multi-tab table (below); it is authored by the user (`ground_truth.measurements`), **compiled by hydromate** from raw sources declared in `ground_truth.sources` (a list of `{category, kind, values, positions, join_key}`), or - the recommended, consistent route - compiled from the **calibration-target template** (`hydromate targets <config>` → `user-sources/ground-truth/calibration-target-data.xlsx`, referenced under `ground_truth.targets` with per-tab position layers `hydraulics_positions`/`sediment_positions`; `src/hydromate/targets.py`, tests in `tests/test_targets.py`). The template's rows are keyed by **unique IDs** joining the point gpkg/shp layers (any CRS, reprojected on ingest; explicit x/y win); its `hydraulics` tab carries u_x/u_y/u_z + fluctuations u_x'/u_y'/u_z' with auto-derived U_h/U_h'/TKE (live Excel formulas, recomputed on ingest → tidy `u_mag`/`u_mag_std`/`tke`), water depth and bottom elevation - and is populated from SonTek FlowTracker2 exports by `src/hydromate/flowtracker.py` (`read_flowtracker`/`fill_template_hydraulics`, tests in `tests/test_flowtracker.py`), auto-detecting the three real layouts (`.ft.sum`, TKE-stats, multi-sheet `FT_TKE_Summary`) keyed by each point's own ID; **the fluctuations u' are the sample standard deviation (`u std`/`Std Dev v'(x)`/σ), NOT the `VxErr` columns** (`VxErr` is the standard error of the mean ≈ std/√Npts) - where only a plain `.ft.sum` (VxErr + Npts, no std-dev) is given, u' is reconstructed as `VxErr·√Npts`; `write_target_template` drops a co-located runnable `extract_flowtracker.py` next to the xlsx that calls `fill_template_hydraulics`; its `morphodynamics` tab carries d16..d90 [mm → m] + fine fraction < 1 mm and auto-samples the **DoD raster into a per-point `dz` column** on ingest (the DoD→targets adapter); its `parameters` tab is a drop-down over `targets.PARAMETER_CATALOG` (verified TELEMAC-2D/3D/GAIA keywords: friction zones prefilled with current ks, CLASSES SHIELDS PARAMETERS, MINIMUM VALUE OF DEPTH, VELOCITY DIFFUSIVITY, secondary-currents coefficients, GAIA transport knobs, ...) with min/max test ranges + tips, ingested by `targets.read_target_parameters` and merged over `calibration.parameters` in `emit_hbc_config` (template wins; `calibration.merged_parameters`). The **hydraulics/FlowTracker path is also implemented** (`kind: flowtracker` joins `.ft.sum` values to a DGPS position layer; `kind: points` reads a layer that already carries quantities). **Still to build:** the sediment/GSD adapter into GAIA `sediment_classes` (the GSD values now land in the tidy `morphodynamics` tab but are not yet folded into the GAIA `.cas`).

**Positions vs. values are split across two folders, joined by `ID`/row order:**
- Measurement **positions** are point shapefiles under `cases/example-Inn/user-sources/geodata/` - and are in **different CRSs than the project's 25832, so they must be reprojected on ingest**:
  - `geodata/flowtracker2/dgps-flowtracker-day{1,2}_utm33.shp` - EPSG:**25833** (UTM 33N). Columns `ID, E_25833, N_25833, WaterDepth, z` (z = bed elevation). 15 points (day1) / 30 (day2).
  - `geodata/sediment/MultiPAC-Mar2020-KB15.shp` - EPSG:**32632** (WGS84/UTM 32N). `name` = Surface/Subsurface. NB its `x`/`y` *attribute* columns are swapped vs the geometry - trust the geometry.
- Measured **values** live under `cases/example-Inn/user-sources/ground-truth/`:
  - **Hydraulics - `hydraulics/FlowTracker2-KB15-day{1,2}.xlsx`**: SonTek FlowTracker2 `.ft.sum` exports for KB15. One sheet; row 0 = metadata (total `DISCHARGE` [CMS], reference gauge), row 1 = headers, row 2 = units, rows 3+ = one vertical each (joins 1:1 by `ID` to the DGPS shp). Key columns: `MeasD`/`FinalD` depth [m]; `VelX/VelY/VelZ` [m/s] (+ `VxErr/VyErr/VzErr`) → velocity components / scalar velocity.
  - **Sediment - `sediment/GSDs-Uni-Stuttgart.xlsx`**: surface & subsurface grain-size distributions (cumulative + fractional) with d65/d84; feeds GAIA `sediment_classes`.

**Target tidy model (generic, source-agnostic):** a multi-tab table - one tab per category (`hydraulics`, `sediment`, …), first 3 columns `x, y, z` (in the project CRS 25832), then quantity columns (FlowTracker hydraulics → `u, v, w, u', v', w', h`). FlowTracker is only one possible source; many ground-truth sources are conceivable, so the reader stays generic and per-source adapters feed it.

**Topographic change**: the DEM-of-Difference (`dem.dem_of_difference`, dem-2020 vs DEM-2025-20cm) is the bed-change ground truth for the GAIA / topographic-change calibration. It is produced in pre-processing when `dem_of_difference.enabled` (the `inn-2020-25` case enables it, 2020→2025), clipped to the ROI and thresholded by a **minimum level of detection** (propagated survey uncertainty `t·√(u_i²+u_t²)` or an explicit `min_lod`; sub-LoD change masked/zeroed) - see stage 1 above and the `dem_of_difference` config block. The DoD raster is **not yet** turned into per-point HydroBayesCal targets (the remaining adapter).

**xlsx gotcha:** these *FlowTracker/GSD* files break `openpyxl`'s style parser (`PatternFill ... unexpected keyword 'extLst'`), so `pandas.read_excel` fails on them on every available env. Read them by unzipping the workbook and parsing `xl/worksheets/sheet1.xml` + `xl/sharedStrings.xml` directly (the `.ft.sum` layout is stable), or with a defensive openpyxl wrapper - don't assume `read_excel` works on these inputs. (`openpyxl` itself **is** in `hydromate-env` - `convergence.ConvergenceReport.to_xlsx` uses it to *write* the styled convergence report fine; the issue is only *reading* those specific styled inputs.)

## Working conventions

- Large rasters (the DEMs/orthos run to hundreds of MB) - don't open them blindly; use `gdalinfo`/`rasterio` to read headers, and window/downsample for any processing.
- Keep raw input data immutable. Generated artifacts go under the configured phase dirs in `cases/example-Inn/hydromate-case/` (preprocessing/ simulation/ postprocessing/ mesh-convergence/ calibration-validation/), not mixed into `user-sources/`.
- This **is** a git repository (default branch `main`). Per-case `user-sources/` (input data) and `hydromate-case/` (produced artifacts) are large/local and gitignored; only the package, the case config + scripts, and docs are tracked.
